Chương 1: Tổng Quan, Đánh Đổi & Bản Chất Của Caching

1.1. Cache là gì? Tấm khiên bảo vệ Database (Shield for DB)

Cache là một thành phần phần cứng hoặc phần mềm dùng để lưu trữ tạm thời các dữ liệu thường xuyên được truy cập, giúp phục vụ các yêu cầu tương lai nhanh hơn gấp hàng chục đến hàng trăm lần.

Dữ liệu trong Cache gồm 2 loại:

  • Bản sao dữ liệu từ nguồn gốc (A copy from DB): Giảm tải đọc cho Database.
  • Kết quả của một phép tính toán phức tạp (Computation Result): Ví dụ: Bảng tổng kết doanh thu lũy tiến của chuỗi Maycha, kết quả tổng hợp sau khi join 5 bảng.
Mô hình: Cache đóng vai trò Tấm Khiên (Shield) chắn trước Database
Client / App
── 1. Hỏi trước ──▶
⚡ REDIS CACHE (0.1ms)
── 2. Chỉ khi Miss mới xuống ──▶
🐘 POSTGRESQL (20ms)

1.2. Hai Sự Đánh Đổi Bắt Buộc (The Inevitable Trade-offs)

  • Performance vs Cost (Hiệu năng vs Chi phí): Bộ nhớ RAM (Redis) đắt hơn ổ cứng SSD từ 10 đến 20 lần. Không ai có thể cache toàn bộ database vào RAM.
  • Performance vs Consistency (Hiệu năng vs Tính nhất quán): Càng muốn đọc nhanh thì nguy cơ đọc phải dữ liệu cũ (Stale Data) càng cao. Bạn phải chấp nhận Eventual Consistency (Nhất quán cuối cùng).

1.3. Chỉ số Hit Rate & Nguyên lý Pareto 80/20

Cache Hit Rate là thước đo sống còn duy nhất của một hệ thống Caching: Hit Rate = (Số lần trúng Cache) / (Tổng số request).

Luôn tuân theo Nguyên lý Pareto 80/20: Trong thực tế, 80% lưu lượng truy cập chỉ xoay quanh 20% dữ liệu nóng (Hotspot Data). Bạn chỉ cần cache đúng 20% dữ liệu này (như danh mục món bán chạy, thông tin cửa hàng mở cửa) là đã bảo vệ được 80% tải của database.

1.4. Phân biệt sống còn: Cache != Buffer

Tiêu chí CACHE (Bộ đệm dữ liệu lặp lại) BUFFER (Vùng đệm chuyển tiếp dữ liệu)
Mục đích Tăng tốc độ đọc cho các request tương lai cùng hỏi 1 dữ liệu. Điều hòa sự chênh lệch tốc độ giữa bên gửi và bên nhận (chống nghẽn).
Vòng đời dữ liệu Dữ liệu được lưu giữ lâu dài (đến khi hết hạn TTL hoặc bị xóa). Dữ liệu chỉ lưu tạm thời, truyền xong là xóa ngay.
Bản chất hoạt động Bản sao dữ liệu để tái sử dụng nhiều lần. Hoạt động giống như một Hàng đợi (Queue / FIFO).

1.5. Các vị trí Caching trong hệ thống hiện đại

  1. Client Cache: Bộ nhớ trình duyệt (HTTP Cache, LocalStorage).
  2. CDN (Content Delivery Network): Cache ở các trạm viễn thông gần người dùng nhất (Cloudflare, Akamai) cho ảnh, video, CSS, JS.
  3. API Gateway / Reverse Proxy: NGINX Cache, Kong Cache.
  4. Application Local Cache: Cache ngay trong RAM của tiến trình Node.js (In-memory Map, NodeCache) ➔ Siêu nhanh nhưng tốn RAM app.
  5. Distributed Cache: Redis Cluster, Memcached ➔ Phổ biến nhất, chia sẻ chung cho nhiều server.
  6. Database Query Cache: Bộ đệm trang trong RAM của chính PostgreSQL (Shared Buffers).

Chương 2: Toàn Cảnh Các Chiến Lược Đọc / Ghi Cache

2.1. Các chiến lược ĐỌC (Read Strategies)

Chiến lược 1: Read-Aside (Cache-Aside) — Chuẩn mực phổ biến nhất
Ứng Dụng (NestJS)
── (1) Đọc Cache ──▶
Redis

Nếu Cache Miss ➔ (2) App tự đọc Database ➔ (3) App tự ghi ngược lại vào Redis.

  • Ưu điểm: Chịu lỗi cực tốt. Nếu Redis bị sập, App vẫn gọi thẳng vào DB để hoạt động tiếp. Cực kỳ linh hoạt với mô hình dữ liệu.
  • Nhược điểm: Logic dồn lên vai ứng dụng; có nguy cơ đọc phải dữ liệu cũ nếu DB thay đổi.
Chiến lược 2: Read-Through

App chỉ nói chuyện với Cache Provider. Nếu Cache Miss, chính hệ thống Cache tự đi kết nối DB, nạp dữ liệu rồi trả về cho App. App coi Cache như một database duy nhất.

2.2. Các chiến lược GHI (Write Strategies)

Chiến lược ghi Cơ chế hoạt động Ưu điểm Nhược điểm & Rủi ro
1. Write-Through Ghi đồng thời vào Cache và Database trong cùng một thao tác. Dữ liệu trong Cache luôn tươi mới 100%. Ghi chậm (Latency cao vì phải đợi cả 2 bên ghi xong).
2. Write-Back (Write-Behind) Ghi vào Cache trước rồi trả về ngay. Gom cụm (Batch) ghi xuống DB sau một cách bất đồng bộ. Tốc độ ghi siêu nhanh (vài microsecond). CỰC KỲ NGUY HIỂM: Nếu server Redis sập trước khi kịp sync xuống DB ➔ MẤT DỮ LIỆU VĨNH VIỄN!
3. Write-Around (Chuẩn kết hợp với Read-Aside) Bỏ qua Cache, ghi thẳng vào Database. Sau đó gửi lệnh XÓA (Invalidate) dữ liệu trong Cache. Tách rời hệ thống Cache và Storage; DB luôn nắm sự thật. Lần đọc tiếp theo chắc chắn bị Cache Miss 1 lần để nạp lại.

Chương 3: Cuộc Chiến Bất Đồng Bộ Dữ Liệu & Bí Quyết "Update DB Trước, Xóa Cache Sau"

Trong ngành Khoa học Máy tính có một câu nói bất hủ của Phil Karlton:

“There are only two hard things in Computer Science: cache invalidation and naming things.”

3.1. Thử nghiệm 1: Khi có dữ liệu mới, UPDATE Cache hay DELETE Cache?

  • Nếu Update Cache: Sẽ bị Race Condition giữa 2 thao tác ghi (Write-Write Conflict). Ví dụ: Request 1 ghi DB trước nhưng mạng lag nên ghi Cache sau; Request 2 ghi DB sau nhưng ghi Cache trước ➔ DB mang giá trị mới, nhưng Cache mang giá trị cũ vĩnh viễn!
  • Kết luận 1: Khi sửa dữ liệu, TUYỆT ĐỐI KHÔNG UPDATE CACHE, MÀ PHẢI DELETE CACHE! Xóa đi để lần đọc tiếp theo tự nạp lại từ DB.

3.2. Thử nghiệm 2: Xóa Cache trước hay Cập nhật DB trước? (Trọng tâm phỏng vấn Senior)

KỊCH BẢN TỬ THẦN NẾU: XÓA CACHE TRƯỚC, UPDATE DB SAU (Delete Cache First)
1. Luồng Ghi (Thread A): Cần sửa giá trị từ 10 thành 20. Thread A xóa Cache trước.
2. Luồng Đọc (Thread B) ập vào ngay lúc đó: Đọc Cache ➔ Thấy Cache trống (Miss)!
3. Thread B đọc DB ➔ Lúc này Thread A chưa update DB xong, nên DB vẫn mang giá trị cũ là 10.
4. Thread B bốc giá trị cũ 10 nạp ngược lại vào Cache.
5. Lúc này Thread A mới update DB thành 20.
👉 HẬU QUẢ: DB là 20, nhưng Cache bị dính chặt giá trị 10 cũ mèm cho đến khi hết hạn TTL!
KỊCH BẢN CHUẨN MỰC THẾ GIỚI: UPDATE DB TRƯỚC, XÓA CACHE SAU (Cache-Aside + DWA)
1. Luồng Ghi (Thread A): Cập nhật DB thành 20 xong xuôi.
2. Thread A gửi lệnh XÓA Cache.
3. Luồng Đọc tiếp theo: Thấy Cache trống ➔ Đọc DB lấy được giá trị mới 20 ➔ Nạp lại Cache.
👉 TẠI SAO CÁCH NÀY THẮNG? Vì tốc độ ghi Cache nhanh gấp hàng chục lần tốc độ ghi đĩa của DB, nên xác suất một câu lệnh đọc chen ngang giữa lúc ghi là cực kỳ hiếm hoi.

3.3. Giải pháp giảm thiểu tối đa rủi ro bất đồng bộ:

  • Luôn gắn Short TTL (Time-To-Live ngắn): Cho dù kịch bản xấu nhất xảy ra, sau vài chục giây dữ liệu trong cache cũng tự bốc hơi.
  • Delayed Double Delete (Xóa 2 lần trễ): Xóa Cache ➔ Update DB ➔ Chờ 500ms ➔ Xóa Cache lần 2 để quét sạch mọi dữ liệu rác vừa bị nạp đè.

Chương 4: Tứ Đại Căn Bệnh Của Hệ Thống Caching & Toa Thuốc Điều Trị

4.1. Bệnh 1: No Atomicity (Thiếu tính nguyên tử khi xóa Cache)

  • Hiện tượng: Update Database thành công, nhưng lệnh xóa Redis bị đứt cáp / timeout ➔ Dữ liệu cũ vẫn nằm trong Cache.
  • Toa thuốc:
    • Cơ chế Retry: Đẩy lệnh xóa cache vào Queue (BullMQ / RabbitMQ) để tự động retry với Exponential Backoff.
    • Lắng nghe Binlog (Change Data Capture - CDC): Dùng công cụ Debezium / Canal đọc trực tiếp WAL Log của PostgreSQL. Khi DB ghi nhận commit thành công, CDC tự động bắn message ra xóa Cache.

4.2. Bệnh 2: Cache Avalanche (Tuyết Lở Caching)

  • Hiện tượng: Một lượng khổng lồ các Key cùng hết hạn tại một thời điểm (ví dụ cấu hình TTL tròn 1 tiếng cho toàn bộ sản phẩm Maycha), HOẶC cụm Redis bị sập ➔ Hàng triệu request cùng ập thẳng xuống Database ➔ Database sập theo dây chuyền!
  • Toa thuốc:
    • Thêm Random Jitter vào TTL: Thay vì đặt TTL = 3600s cứng, ta đặt: TTL = 3600 + Math.random() * 300 (dao động lệch nhau từ 1 đến 5 phút) để các key hết hạn rải rác.
    • Triển khai Redis Cluster (Sentinel / Master-Replica): Đảm bảo tính sẵn sàng cao (High Availability), node này chết có node khác thay ngay.
    • Circuit Breaker & Rate Limiting: Tự động ngắt bớt request nếu DB có dấu hiệu quá tải.

4.3. Bệnh 3: Cache Breakdown / Cache Stampede (Đàn Bò Giẫm Đạp)

  • Hiện tượng: Một Hot Key cực kỳ quan trọng (ví dụ: Voucher 50% giờ vàng hoặc Menu quán Maycha) vừa hết hạn TTL ➔ Trong đúng 1 giây đó có 10.000 request cùng hỏi ➔ Cả 10.000 request cùng thấy Cache Miss ➔ Cùng lao xuống DB query ➔ DB bị giẫm bẹp!
  • Toa thuốc:
    • Mutex Lock (Singleflight): Khi thấy Cache Miss, chỉ cho phép request ĐẦU TIÊN được cầm chìa khóa (Distributed Lock) chạy xuống DB, 9.999 request còn lại phải đứng đợi. Khi request 1 nạp cache xong thì 9.999 request kia lấy từ Cache ra.
    • Không set TTL cho Hot Data: Cập nhật dữ liệu bằng Background Worker chạy ngầm định kỳ trước khi hết hạn.

4.4. Bệnh 4: Cache Penetration (Xuyên Thủng Cache)

  • Hiện tượng: Hacker hoặc bug liên tục truy vấn dữ liệu KHÔNG HỀ TỒN TẠI (ví dụ: `ID = -9999` hoặc chuỗi rác ngẫu nhiên). Cache Miss ➔ Xuống DB cũng Miss ➔ Không có gì để ghi vào Cache ➔ Mọi request tiếp theo lại tiếp tục đâm thẳng xuống DB!
  • Toa thuốc:
    • Cache giá trị rỗng (Cache Null/Empty): Lưu `key: null` với TTL ngắn (30s – 60s) để chặn đứng các request trùng lặp tiếp theo.
    • Validate chặt chẽ đầu vào: Dùng Zod / DTO chặn ngay ID âm, ID sai regex từ cửa ngõ API.
    • Bloom Filter: Sử dụng bộ lọc xác suất Bloom Filter đặt trước Redis. Nếu Bloom Filter bảo *"Dữ liệu này không tồn tại"*, ta từ chối ngay lập tức mà không cần chạm vào Redis hay DB!

Chương 5: Vấn Đề Tải Cao (Hot Keys, Large Keys) & Thuật Toán Dọn Bộ Nhớ

5.1. Xử lý Hot Keys (Key nhận traffic đột biến)

  • Nhân bản Key (Key Partitioning): Nhân bản key `hot_item` thành `hot_item_1`, `hot_item_2`... `hot_item_N` và phân tán sang các Redis Nodes khác nhau. Client random chọn node để đọc, chia đều tải.
  • Local In-Memory Cache: Caching ngay trong bộ nhớ RAM của App Node.js (ví dụ dùng thư viện `lru-cache`) để chặn 99% request trước khi kịp bay ra Redis.

5.2. Xử lý Large Keys (Key có dung lượng quá lớn > 1MB)

  • Redis chạy đơn luồng. Đọc một Large Key 10MB sẽ làm nghẽn toàn bộ Redis trong vài mili-giây!
  • Giải pháp: Nén dữ liệu bằng Gzip/Snappy trước khi lưu; chia nhỏ key (Split); hoặc chuyển sang lưu file trên S3 / MinIO thay vì nhồi vào Redis.

5.3. Thuật toán dọn dẹp khi đầy bộ nhớ (Cache Replacement Policies)

Khi Redis chạm ngưỡng RAM tối đa (`maxmemory`), nó phải vứt bớt key cũ theo thuật toán nào?

Thuật toán Cơ chế hoạt động Trường hợp áp dụng
LRU (Least Recently Used) Xóa các key đã lâu nhất không được ai gọi tới. Phổ biến nhất. Phù hợp với dữ liệu có tính chất theo trend (hết trend là bị xóa).
LFU (Least Frequently Used) Xóa các key có tổng số lần được gọi ít nhất. Phù hợp với dữ liệu cần giữ lại các item siêu hot dù nó vừa bị ngưng một chút.

6.1. Ứng dụng thực tế vào hệ thống Quản lý hợp đồng Maycha

6.2. Bài tập thực hành (Homework Slide 43)

Đề bài: Xây dựng một module Local In-Memory Cache lưu danh sách các Sân Bay (Airport Code, Tên sân bay) theo mô hình Read-Aside kèm TTL.

Code Mẫu NestJS Hoàn Chỉnh:

import { Injectable, Logger } from '@nestjs/common';

export interface Airport {
  code: string;
  name: string;
}

@Injectable()
export class AirportCacheService {
  private readonly logger = new Logger(AirportCacheService.name);
  // Sử dụng Map làm In-Memory Local Cache
  private readonly cache = new Map<string, { data: Airport; expiresAt: number }>();

  // Mô hình Read-Aside
  async getAirport(code: string): Promise<Airport | null> {
    const cached = this.cache.get(code);
    const now = Date.now();

    // 1. CACHE HIT
    if (cached && cached.expiresAt > now) {
      this.logger.log(`⚡ [CACHE HIT] Sân bay: ${code}`);
      return cached.data;
    }

    // 2. CACHE MISS -> Đọc từ nguồn gốc
    this.logger.warn(`❌ [CACHE MISS] Sân bay: ${code} -> Đang nạp từ nguồn...`);
    const airport = await this.fetchFromDatabaseOrApi(code);
    if (!airport) return null;

    // 3. Ghi ngược lại vào Cache với TTL 60s + Random Jitter (chống Avalanche)
    const ttlSeconds = 60 + Math.floor(Math.random() * 10);
    this.cache.set(code, {
      data: airport,
      expiresAt: now + ttlSeconds * 1000,
    });

    return airport;
  }

  // Giả lập đọc nguồn DB gốc (chậm 200ms)
  private async fetchFromDatabaseOrApi(code: string): Promise<Airport | null> {
    await new Promise((r) => setTimeout(r, 200));
    const airports: Record<string, string> = {
      SGN: 'Sân bay Quốc tế Tân Sơn Nhất - TP.HCM',
      HAN: 'Sân bay Quốc tế Nội Bài - Hà Nội',
      DAD: 'Sân bay Quốc tế Đà Nẵng',
    };
    if (!airports[code]) return null;
    return { code, name: airports[code] };
  }
}
