Mục tiêu: chọn kiểu cho mỗi cột bằng một con số đo được (byte, độ lệch, mã lỗi), không theo thói quen MySQL.

LÀ GÌ?
Kiểu cột quyết định số byte, phép so sánh, và lỗi nào DB chặn hộ bạn.
TẠI SAO?
Sai kiểu không báo lỗi ngay. Nó lệch tiền, lệch giờ, hoặc làm query trả 0 dòng một cách im lặng.
KHI NÀO KHÔNG?
Đừng tiết kiệm byte bằng float cho tiền hay timestamp cho thời điểm. 4 byte không đáng một lần lệch sổ.

Slide 22 · MySQL đúng, PG khác
Slide nói

VARCHAR cho chuỗi ngắn; TEXT nằm ở vùng lưu riêng, MySQL không index được cả chuỗi TEXT.

PG 16 đo được

text và varchar(255) tốn như nhau: 12 byte cho "xin chao". Chuỗi dài được nén (TOAST): 11120 byte còn 148. Giới hạn index là của B-tree, không phải của kiểu: giá trị quá 2704 byte báo 54000, dù cột là text hay varchar.

-- #region string · text và varchar(255) tốn đúng như nhau trên PG (slide 22)
SET search_path = lab07_modeling;  -- DB mặc định trỏ vào lab03_indexing
SET statement_timeout = '60s'; SET lock_timeout = '5s';
SELECT pg_column_size('xin chao'::text) AS text_8_ky_tu, pg_column_size('xin chao'::varchar(255)) AS varchar255_8_ky_tu,
       pg_column_size(repeat('a', 3000)::text) AS text_3000_ky_tu;
-- Chuỗi dài lưu trong bảng được nén (TOAST) khi vượt khoảng 2 KB: 10.000 ký tự lặp chỉ còn vài trăm byte.
DROP TABLE IF EXISTS ty_samples;
CREATE TABLE ty_samples (id int PRIMARY KEY, note text);
INSERT INTO ty_samples VALUES (1, repeat('món ngon ', 1112));
SELECT length(note) AS so_ky_tu, octet_length(note) AS so_byte_goc, pg_column_size(note) AS so_byte_luu_that FROM ty_samples;
-- Giá trị ngắn khi nằm trong bảng dùng header 1 byte, nên nhỏ hơn con số đo trên literal ở trên.
DROP TABLE IF EXISTS ty_stored;
CREATE TABLE ty_stored (t text, v varchar(255), n numeric(12,2));
INSERT INTO ty_stored VALUES ('xin chao', 'xin chao', 123456.78);
SELECT pg_column_size(t) AS text_trong_bang, pg_column_size(v) AS varchar_trong_bang, pg_column_size(n) AS numeric_trong_bang FROM ty_stored;
-- #endregion

Slide 23 · MySQL đúng, PG khác
Slide nói

Số nguyên dùng loại nhỏ nếu đủ; INT(1) giống INT(9). Tiền không dùng FLOAT/DOUBLE, dùng DECIMAL.

PG 16 đo được

smallint/int/bigint = 2/4/8 byte; numeric(12,2) cho 123456.78 đo trên literal là 12 byte, nằm trong bảng còn 9 byte. "Nhỏ" phải còn chỗ: 2147483647 + 1 báo 22003. PG không có cú pháp INT(1): SELECT 1::int(1) báo 42601, vì đó là độ rộng hiển thị riêng của MySQL. Phần lời khuyên (số nhỏ đủ dùng, tiền không dùng float) thì đúng nguyên trên PG.

Làm mẫu · vì sao tiền không bao giờ là float
  1. Chạy region money bên dưới. Dòng đầu: 0.1 + 0.2 bằng float ra 0.30000000000000004, và phép so sánh với 0.3 ra f. Lý do: 0,1 không biểu diễn đúng được trong hệ nhị phân, máy lưu số gần nhất.
  2. Sai số nhỏ cộng dồn: cộng 0,1 một triệu lần ra 100000.00000133288, còn numeric ra đúng 100000.0.
  3. Dữ liệu thật: northwind lưu đơn giá và chiết khấu bằng real. So cùng một cách tính mới công bằng. Không làm tròn: float ra 1265793.038653364, numeric ra 1265793.0395, lệch chưa tới 0,001. Làm tròn từng dòng về 2 số lẻ như in hóa đơn: float ra 1265792.95, numeric ra 1265793.29. Float cho ra những giá trị kiểu 0,0749999 nên làm tròn sai ở các dòng "x,xx5", cộng lại lệch hẳn 34 xu so với sổ sách.
  4. Kết luận cho quán: giá món là numeric(12,2) (hoặc bigint đếm đồng, vì VND không có xu). Prisma: Decimal @db.Decimal(12,2), ở Node đọc ra là Decimal, đừng ép sang number trước khi cộng.
-- #region money · Tiền không bao giờ dùng float (slide 23)
SET search_path = lab07_modeling;  -- DB mặc định trỏ vào lab03_indexing
SET statement_timeout = '60s'; SET lock_timeout = '5s';
SELECT 0.1::float8 + 0.2::float8 AS float_cong, (0.1::float8 + 0.2::float8) = 0.3 AS float_bang_0_3,
       0.1::numeric + 0.2::numeric AS numeric_cong;
-- Cộng 0,1 một triệu lần:
SELECT sum(0.1::float8) AS tong_float, sum(0.1::numeric) AS tong_numeric FROM generate_series(1, 1000000);
-- Dữ liệu thật: northwind lưu đơn giá, chiết khấu bằng real (float 4 byte). So cùng một cách tính:
-- (1) không làm tròn: float lệch rất nhỏ; (2) làm tròn từng dòng về 2 số lẻ như hóa đơn: float lệch hẳn.
SELECT sum(unit_price * quantity * (1 - discount)) AS real_khong_lam_tron,
       sum(unit_price::numeric * quantity * (1 - discount::numeric)) AS numeric_khong_lam_tron,
       sum(round((unit_price * quantity * (1 - discount))::numeric, 2)) AS real_lam_tron_tung_dong,
       sum(round(unit_price::numeric * quantity * (1 - discount::numeric), 2)) AS numeric_lam_tron_tung_dong
FROM order_sheet;
-- #endregion

Slide 24 · MySQL đúng, PG khác
Slide nói

TIMESTAMP ít byte nhưng giới hạn năm; DATETIME dễ đọc, không giới hạn, phụ thuộc múi giờ. Nên lưu kèm múi giờ, mọi nơi đặt múi giờ 0.

PG 16 đo được

timestamptz và timestamp đều 8 byte. timestamptz lưu một thời điểm: 9 giờ sáng Việt Nam đọc ở phiên UTC thành 2026-10-28 02:00:00+00. timestamp chỉ lưu chữ số trên đồng hồ, đọc ở đâu cũng 2026-10-28 09:00:00, không ai biết đó là giờ nào. Năm 2100 lưu bình thường.

-- #region time · timestamptz lưu một thời điểm; timestamp chỉ lưu "chữ số trên đồng hồ" (slide 24)
SET search_path = lab07_modeling;  -- DB mặc định trỏ vào lab03_indexing
SET statement_timeout = '60s'; SET lock_timeout = '5s';
SELECT pg_column_size(now()) AS timestamptz_byte, pg_column_size(now()::timestamp) AS timestamp_byte, pg_column_size(current_date) AS date_byte;
DROP TABLE IF EXISTS ty_times;
CREATE TEMP TABLE ty_times (co_mui_gio timestamptz, khong_mui_gio timestamp);
SET TimeZone = 'Asia/Ho_Chi_Minh';                       -- app ở Việt Nam ghi lúc 9 giờ sáng
INSERT INTO ty_times VALUES ('2026-10-28 09:00', '2026-10-28 09:00');
SELECT co_mui_gio, khong_mui_gio FROM ty_times;
SET TimeZone = 'UTC';                                    -- server/worker khác đọc lại
SELECT co_mui_gio, khong_mui_gio FROM ty_times;
-- Ép chuỗi có múi giờ vào timestamp: phần +07 bị BỎ, không báo lỗi.
SELECT '2026-10-28 09:00+07'::timestamp AS mat_mui_gio, '2026-10-28 09:00+07'::timestamptz AS giu_thoi_diem;
-- Không có giới hạn năm 2038 như TIMESTAMP của MySQL:
SELECT '2100-01-01 00:00+07'::timestamptz AS nam_2100;
RESET TimeZone;
-- #endregion

Slide 25 · MySQL đúng, PG khác
Slide nói

Nhỏ là tốt, đơn giản là tốt. Tránh NULL vì MySQL khó tối ưu cột nullable.

PG 16 đo được

NULL rất rẻ: dòng có 3 cột NULL (chỉ id có giá trị) 28 byte, dòng có giá trị 63 byte (PG chỉ bật 1 bit). Lý do tránh NULL trên PG là ngữ nghĩa: NOT IN gặp một NULL trả 0 dòng, NOT EXISTS trả 76. UNIQUE cho phép nhiều NULL; muốn chặn thì NULLS NOT DISTINCT (23505).

-- #region null · NULL rẻ khi lưu nhưng có bẫy khi so sánh (slide 25)
SET search_path = lab07_modeling;  -- DB mặc định trỏ vào lab03_indexing
SET statement_timeout = '60s'; SET lock_timeout = '5s';
DROP TABLE IF EXISTS ty_nulls;
CREATE TABLE ty_nulls (id int, a bigint, b bigint, c text);
INSERT INTO ty_nulls VALUES (1, 100, 200, 'có giá trị'), (2, NULL, NULL, NULL);
SELECT id, pg_column_size(t.*) AS byte_ca_dong FROM ty_nulls t ORDER BY id;
-- Bẫy NOT IN: danh sách loại trừ có một NULL → không dòng nào thỏa.
SELECT count(*) AS so_dong FROM nf_products WHERE product_id NOT IN (SELECT x FROM (VALUES (1), (NULL)) v(x));
SELECT count(*) AS so_dong FROM nf_products p WHERE NOT EXISTS (SELECT 1 FROM (VALUES (1), (NULL)) v(x) WHERE v.x = p.product_id);
-- #endregion

Tự làm · chặng 5

Đề: tạo bảng my_menu_items cho chuỗi trà sữa, đúng 10 cột: id, cửa hàng, tên món, giá, tồn kho, ghi chú, trạng thái, tùy chọn (size, topping), created_at, updated_at. Mỗi cột ghi một dòng lý do, và lý do phải dẫn một con số đo được ở chặng này.

PASS khi: so_cot = 10, cot_float = 0, cot_timestamp_khong_mui_gio = 0, cot_varchar255 = 0.

Lời giải mẫu
SET search_path = lab07_modeling;  -- thiếu dòng này thì bảng bị tạo nhầm sang lab03_indexing
DROP TABLE IF EXISTS my_menu_items;
CREATE TABLE my_menu_items (
  id         bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  store_id   bigint NOT NULL,                              -- khóa ngoại: nhớ index (chặng 3)
  name       text NOT NULL CHECK (length(name) <= 120),    -- text = varchar(255): tốn như nhau
  price      numeric(12,2) NOT NULL CHECK (price >= 0),    -- float lệch 0.30000000000000004
  stock_qty  int NOT NULL DEFAULT 0,                       -- 4 byte, trần 2147483647
  note       text,                                         -- NULL được: dòng NULL chỉ 28 byte
  status     text NOT NULL DEFAULT 'ACTIVE' CHECK (status IN ('ACTIVE', 'SOLD_OUT', 'HIDDEN')),
  options    jsonb NOT NULL DEFAULT '{}',                  -- size, topping: thêm khóa không cần ALTER
  created_at timestamptz NOT NULL DEFAULT now(),           -- thời điểm: 09:00+07 = 02:00+00
  updated_at timestamptz NOT NULL DEFAULT now()
);

Prisma tương ứng: price Decimal @db.Decimal(12,2), createdAt DateTime @db.Timestamptz(3) @default(now()), options Json @default("{}"). CHECK không khai báo được trong schema Prisma: thêm tay vào migration.sql.
