# Red team: failure modes (Murphy's Law / Flow Tracer)

Scope: `plan.md` + `phase-01..09`, with the plan.md "Materialization must-fix" section treated as applied. Its 8 items are not re-reported here. Evidence comes from read-only commands on 2026-10-31 (Docker 28.4.0, `advance-be-redis` 7.2.3, Git Bash).

## Finding 1: The Lua A/B timelines call `redis-cli --eval` inside a redis-cli session, which can never work
- **Severity:** Critical
- **Location:** phase-03 "Region design": `06-delay` (line 69), `08-lock` cad/fencing (line 73), `09-bucket` A/B (line 74). Runner contract in phase-02 lines 31-34.
- **Flaw:** `06-delay.B.redis` (and the `08-lock`/`09-bucket` A/B files) are `.redis` files. `run-redis.mjs` streams them into a single `docker exec -i … redis-cli --no-raw` session, and `--ab` only runs two such "timed sessions". `redis-cli --eval file keys , args` is a CLI flag, not a Redis command. The `.redis` file also contains a literal `<now>`, and a static file cannot compute it.
- **Failure scenario:** The runner sends the line `redis-cli --eval /lab/lua/delay-claim.lua …` (or `--eval …`) as a command and gets `ERR unknown command`. R31, R42, R43 and R44 fail on every run. A "fix" that inlines the script as `EVAL "<script>"` duplicates the `.lua` text, so V05 byte-exact `data-cmd` against `lua/*.lua` breaks, or the guide's Lua and the run's Lua drift apart.
- **Evidence:** `printf -- '--eval /lab/x.lua\n' | docker exec -i advance-be-redis redis-cli --no-raw` → `(error) ERR unknown command '--eval', with args beginning with: '/lab/x.lua'`. Also `phase-03-containers-experiments-runs.md:69` ("Lua = `redis-cli --eval /lab/lua/delay-claim.lua l06:delay:orders , <now>`"), `phase-02-tests-first.md:34`.
- **Suggested fix:** Make the region the source of truth. Either (a) in A/B `.redis` files, use `SCRIPT LOAD` once from a `.sh` setup region, then `EVALSHA <sha>`, with the runner substituting `$SHA_<name>`; or (b) add a runner directive `#@ evalfile lua/x.lua KEYS… , ARGV…` that the runner expands to `EVAL "<file text>" n …`, while `displayText` shows the learner the `--eval` one-liner. Compute "now" inside Lua with `redis.call('TIME')`, never as `<now>`.

## Finding 2: The R31 expectation is false with the slide-37 seed, and the naive run eats the Lua run's input
- **Severity:** High
- **Location:** `plan.md:93` (R31 "Lua claim: one gets `o1`, other nil"); phase-03 seed line 56 ("`l06:delay:orders` (3 jobs, slide 37 scores)"); phase-03 line 69 (naive `ZRANGE … LIMIT 0 1` → `RPUSH` → `ZREM`).
- **Flaw:** All three slide-37 scores (1704790435, 1704793232, 1704797344) are January 2024, so every job is due on 2026-10-31. A correct atomic claim gives A `o1` and B `o2`, not nil. The naive timeline also `ZREM`s `o1` (twice) before the Lua timeline runs, and no re-seed sits between them.
- **Failure scenario:** The Lua run shows A=`o2`, B=`o3` (or A=`o1`, B=`o2` after a re-seed). The R31 regex fails, and the controller logs a "deviation" against Redis for what is really a test-design error. The chip "OK" is then argued against data that contradicts the stated claim.
- **Evidence:** `Tài Liệu/advanced_backend/6. Redis.md:470-472` (`o1 u1 1704790435`, `o2 u34 1704793232`, `o3 u88 1704797344`); `plan.md:93`; `phase-03-containers-experiments-runs.md:56`, `:69`.
- **Suggested fix:** The delay region seeds its own ZSET just before each timeline: 1 due job (`o1`, score = now-60 computed in Lua) + 2 future jobs. Assert "A gets `o1`, B gets nil, `o2`/`o3` remain". Every A/B region must start with its own setup and reset lines, not rely on `00-seed`.

## Finding 3: "Each `--ab` pair 3×" plus the rerun gate run on drifting state; manifest semantics are undefined
- **Severity:** High
- **Location:** phase-03 `record-all.sh` step 4.3 (line 79); phase-02 rerun gate line 68; manifest append line 35; M01 line 41.
- **Flaw:** No step resets per-scenario keys between repetitions. Run 2 of `08-lock.nolock` sees the run-1 `BOOKED` entries (expected "2 `BOOKED`" becomes 4). `05-queue`, `09-bucket` (bucket already drained, refill 0.01/s), `02-json-race` and `06-delay` (jobs already `ZREM`ed) all start from the previous run's leftovers. The rerun gate only compares counts of `(error)` lines, so state drift (`NEW`→`IN_PROGRESS`, 10 allowed → 0 allowed) passes it. Also, `runs/manifest.tsv` is append-only, and the plan does not say whether repetitions 2-3 overwrite the run-1 file or which manifest line M01 checks.
- **Failure scenario:** Runs 2-3 differ from run 1, so "compare 2–3" reports variance that is really leftover state. Or the repetitions overwrite `*.timeline.txt`, so the recorded file is run 3, not run 1. M01 then fails on stale earlier lines, or passes against the wrong line. In phase 08, re-running one region appends a second sha for the same file, which gives the same ambiguity.
- **Evidence:** `phase-03-containers-experiments-runs.md:79` ("each `--ab` pair 3× (record run 1, compare 2–3)"); `phase-02-tests-first.md:68` ("second pass must not show more `(error)` lines"); `phase-02-tests-first.md:35`, `:41`; `plan.md:102` (R39 "log has 2 `BOOKED`").
- **Suggested fix:** Every stateful region starts with an explicit `UNLINK` of its own keys (lintable rule: the first command of an A region is `UNLINK`). Repetitions 2-3 write `--out <id>.rep2/.rep3` into `verify/tmp/` and stay out of the manifest. The manifest is rewritten as one row per file (latest sha), not appended. The rerun gate compares normalised outputs (timestamps masked), not error counts.

## Finding 4: Two-client timelines have no start barrier, while `docker exec` startup is about 200 ms and the R41 margin is 100 ms
- **Severity:** High
- **Location:** phase-02 `--ab <A> <B> <region> <delayB>` (line 34); phase-03 `01-block` "`--ab … sleep 0`" (line 59); `08-lock ttldel` "PX 2000 … B acquires at 2.1 s" (line 73); `plan.md:103` (R41), `plan.md:138` (timing-flake mitigation).
- **Flaw:** Each B `#@ sleep` counts from B's own session start, not from A's command reaching the server. The lesson-07 runner this adapts starts A in the background, sleeps, then starts B, with no handshake (`run-lab.sh:30-33`). Must-fix 2 adds host send stamps (detection), but nothing makes the ordering hold. R41 depends on B's `SET NX PX` arriving more than 2000 ms after A's, with only 100 ms of slack. R02 (`sleep 0` + B sleep 0.5) depends on A's `DEBUG SLEEP` landing before B's `PING`.
- **Failure scenario:** A's `docker exec` cold-starts about 150 ms slower than B's (one Defender scan or a WSL hiccup is enough). B's `SET NX` arrives at A+1.95 s, returns nil, and the whole ttldel → `DEL`-steals-lock story is not shown. The plan says "run 1 recorded", so a flaky run 1 becomes the official run or a fake deviation.
- **Evidence:** `for i in 1..5; docker exec advance-be-redis redis-cli PING` → `exec_ms=198, 205, 232, 212, 206` (pure exec overhead, warm). `plans/261027-1328-lesson-07-data-modeling-teacher-guide/verify/run-lab.sh:30-33`; `phase-03-containers-experiments-runs.md:73`; `plan.md:103`.
- **Suggested fix:** `run-redis.mjs --ab` opens both sessions first and waits until each has echoed `@@0` (a ready barrier). Only then does it start the shared clock and release step 1 of A. B's sleeps count from A's `@@k` echo of the command it races against. Widen R41 to PX 2000 with B at +2.5 s. Reject a run (do not record it) whose host-stamp deltas break the ordering, and retry up to 3 times.

## Finding 5: R35 after reconnect is gated by `repl-timeout 60` / ping period 10, so "`GET` 120 + `sync_partial_ok` ≥ 1" will not appear promptly
- **Severity:** High
- **Location:** phase-03 `07-architecture.sh#partition` (line 71: "reconnect → `GET` (120), `sync_partial_ok`"); `plan.md:98` (R35); must-fix 3 (`plan.md:155`) keeps the post-reconnect assertion.
- **Flaw:** Must-fix 3 only removed the `link:down` assertion. After `docker network connect`, one of two things happens. (a) The replica gets a new IP (Docker allocates serially). Both old TCP sockets are then dead, and neither side notices until `repl-timeout` (60 s) passes without traffic, so the replica serves 100 for up to about 60 s. (b) The IP is reused and TCP retransmission revives the old connection. Then no new PSYNC happens, and `sync_partial_ok` stays 0. In neither case does "immediately after reconnect: 120 and `sync_partial_ok` ≥ 1" hold.
- **Failure scenario:** The `.sh` region reads the replica right after `connect` and gets `"100"`, or a later read gets `"120"` with `sync_partial_ok:0`. R35 fails, and W7's partition replay is built on a deviation.
- **Evidence:** `docker exec advance-be-redis redis-cli CONFIG GET repl-timeout` → `60`; `CONFIG GET repl-ping-replica-period` → `10`; `docker version` → `28.4.0`; `phase-03-containers-experiments-runs.md:71`; `plan.md:98`, `:155`.
- **Suggested fix:** After `network connect`, force a resync deterministically: run `CLIENT KILL TYPE replica` on the master (the replica reconnects and does PSYNC from its offset, so `sync_partial_ok` +1). Then poll the replica `GET` until it returns 120 with a 15 s cap, and record the poll count. Or narrate "partial sync happens within repl-timeout" and assert only offsets equal after a poll.

## Finding 6: `99-cleanup.sh` removes network `advance-be-l06` while main is still attached, and the drift check cannot see network or mount
- **Severity:** High
- **Location:** `plan.md:144` (rollback: removes extras "and removes network `advance-be-l06`"; only `--all` removes main); phase-03 lifecycle table line 35 (main on `advance-be-l06`); phase-03 line 44 ("recreates a container only when `docker inspect .Config.Cmd` differs"); phase-09 step 4 line 35 (runs `99-cleanup.sh`, keeps main up).
- **Flaw:** `docker network rm` fails while an endpoint (main) is connected. If the script works around this by disconnecting main, main is off the network. Later, `up replica` recreates `advance-be-l06`, but main's `Config.Cmd` is unchanged, so `00-containers.sh` does not recreate or re-attach it. Network membership and the `-v <labs>:/lab` mount live in `HostConfig`/`NetworkSettings`, not `Config.Cmd`.
- **Failure scenario:** Phase 09 step 4 errors (`error while removing network: network advance-be-l06 has active endpoints`). Under `set -u` without `-e`, the script continues and reports a half-clean state. In the disconnect variant, on study day the learner runs `up replica`, the replica cannot resolve `advance-be-redis`, `master_link_status` stays down, R34 cannot be reproduced, and check C01 "expected network" shows ✘. The same blind spot means a main created from a different clone path keeps a stale `/lab` mount.
- **Evidence:** `plan.md:144`; `phase-03-containers-experiments-runs.md:35`, `:44`; `phase-09-docs-final-gate-handoff.md:35`; current main is on `bridge` with no mount: `docker ps --format '{{.Names}} {{.Networks}}'` → `advance-be-redis bridge`.
- **Suggested fix:** `99-cleanup.sh` (without `--all`) leaves the network in place. The `up` drift check compares Cmd, network list and the mount source (`docker inspect -f '{{.Config.Cmd}}|{{range $k,$v := .NetworkSettings.Networks}}{{$k}}{{end}}|{{range .Mounts}}{{.Source}}{{end}}'`), and `up replica` always runs `docker network connect advance-be-l06 advance-be-redis` if missing (idempotent).

- **Location:** phase-01 step 1 line 22 (fingerprint = every container not `^advance-be-redis`); phase-02 `check.sh` C01-C06 line 45 and C14 line 51; phase-05 prep line 29 (learner runs `check.sh`); phase-09 step 2 line 26 and step 4 line 35; `plan.md:126` (AC 11).

The handoff file is dated 20261101, so the build itself is expected to span that day. Must-fix 7 handles Docker restarts but not a legitimate new container. Separately, `check.sh` C01-C06 require all six containers to exist, but phase 09 step 4 removes the five extras before handoff. The learner's first prep `check.sh` therefore prints at least 5 ✘ plus the C14 ✘, and exits non-zero.
- **Failure scenario:** Phase 09's "fingerprint before = after" fails for a reason unrelated to the lesson, which pushes the controller toward re-baselining (and so hides any real collateral damage). On 2026-11-02, Đạt runs the prescribed prep check, sees 6 red rows on a correct setup, and loses trust in every later ✔/✘ self-check.
- **Evidence:** `plans/261027-0907-cluster1-m0-m1-implementation/phase-02-khung-repo-m0.md:35` (`container_name: omnipos-hub-pg`), `:38` (`127.0.0.1:5434:5432`); `evidence-packet.md:12-13` (Phase B tomorrow, study after it); `phase-01-contract-baseline-smoke.md:22`; `phase-02-tests-first.md:45`, `:51`; `phase-05-guide-shell-assembler.md:29`; `phase-09-docs-final-gate-handoff.md:21`, `:26`, `:35`.
- **Suggested fix:** Change the fingerprint to the set of containers present at baseline, each with id/image/Up-Exited. New containers outside `advance-be-redis*` are reported but are not a failure, and a removed or changed baseline container is a failure. Move C14 out of the learner's `check.sh` into `verify/` (controller-only). `check.sh <stage>` checks only the containers that stage needs; the default `check.sh` checks main only.

## Finding 8: Learner-facing `.sh` lines and `docker exec … /path` commands get mangled by Git Bash; the runner's `MSYS_NO_PATHCONV=1` hides it
- **Severity:** High
- **Location:** phase-02 runner line 33 (".sh regions run as `bash -c` … `MSYS_NO_PATHCONV=1` is set"); phase-03 line 45 ("mounts with `MSYS_NO_PATHCONV=1` and `pwd -W`"); phase-03 `04-persistence.sh` line 67 (`ls /data/appendonlydir`, `head -c 5` base file); phase-03 line 69 (`--eval /lab/lua/...`).
- **Flaw:** The recorded runs set `MSYS_NO_PATHCONV=1` in the runner's environment, but the learner pastes or runs the same lines in Git Bash. Nothing requires each learner `.sh` file to export it itself, and the guide's `pre[data-cmd]` would not show it. In addition, `pwd -W` in `00-containers.sh` resolves the caller's cwd. The prep line runs from the repo root (`bash labs/lesson-06-redis/00-containers.sh up main`), so `/lab` would be the repo root and `/lab/lua/*.lua` would not exist.
- **Failure scenario:** Đạt runs `docker exec advance-be-redis-aof ls /data/appendonlydir` and Docker receives `D:/Git/data/appendonlydir`, so the result is "No such file", while the guide's recorded run shows the listing. Every `/lab/lua/...` reference breaks the same way. All recorded runs pass while the learner's runs fail, which is exactly the trust break the "run it yourself" format cannot absorb.
- **Evidence:** `docker exec advance-be-redis echo /data/appendonlydir /lab/lua/x.lua` (Git Bash) → `D:/Git/data/appendonlydir D:/Git/lab/lua/x.lua`; with `MSYS_NO_PATHCONV=1` → `/data/appendonlydir`. `phase-02-tests-first.md:33`; `phase-03-containers-experiments-runs.md:45`, `:67`; `phase-05-guide-shell-assembler.md:29`.
- **Suggested fix:** Every learner `.sh` starts with `export MSYS_NO_PATHCONV=1` and `HERE="$(cd "$(dirname "$0")" && pwd -W)"`, and mounts `$HERE`. The runner must NOT set `MSYS_NO_PATHCONV` itself, so recorded runs prove the file works as shipped. Add a V16 lint rule: `.sh` file missing the export → fail. In `#cach-hoc`, show the PowerShell form for one-off `docker exec … /path` lines, or prefix them `MSYS_NO_PATHCONV=1`.

## Finding 9: R22 kills `-rdb` without waiting for `BGSAVE` to finish
- **Severity:** Medium
- **Location:** `plan.md:84` (R22 "`BGSAVE`; 500 more; `docker kill`; start → DBSIZE 1000"); phase-03 `04-persistence.sh` line 67 (no wait step for rdb, only for `aof_rewrite_in_progress`).
- **Flaw:** `BGSAVE` returns "Background saving started" immediately. The child writes `temp-<pid>.rdb` and renames it to `dump.rdb` only when done. The plan waits for the AOF rewrite to finish but not for `rdb_bgsave_in_progress:0`, and does not check `rdb_last_bgsave_status:ok` before the kill.
- **Failure scenario:** On a loaded WSL VM, the awk write of 500 keys plus `docker kill` arrives before the child renames. After `docker start`, DBSIZE is 0 (or the previous run's dump), not 1000, so R22 fails or records a misleading "RDB lost everything". The second run inherits the old `dump.rdb` from the anonymous volume, and the number becomes non-deterministic between runs.
- **Evidence:** `plan.md:84`; `phase-03-containers-experiments-runs.md:67`; `phase-03-containers-experiments-runs.md:48` (anonymous `/data` volume survives `docker start`).
- **Suggested fix:** After `BGSAVE`, poll `INFO persistence` until `rdb_bgsave_in_progress:0` and `rdb_last_bgsave_status:ok`, and record `rdb_last_save_time`. Start each persistence region with `FLUSHALL` + `SAVE` on its own container, so a leftover dump cannot pass the assertion.

## Finding 10: The homework checker cannot fail H1 for the bad fixture, and H5's "slow holder" cannot be injected into "any language"
- **Severity:** Medium
- **Location:** phase-04 lines 31-39 (contract, H1, H5, bad fixture "expected to fail H1 and H2"); test matrix line 59 ("✘ H1, H2 (H5 ✘)"); `plan.md:109` (R47).
- **Flaw:** The booking is a single key `l06:hw:booking:FA634:A34_S012C`. A GET-then-SET race makes both requests `SET` the same key, so there is still exactly 1 booking key and H1 passes. Only H2 (two `BOOKED`) catches the race. H5 needs "a slow holder" with `HW_TTL_MS=50`, but the contract defines no hold-time input (for example `HW_HOLD_MS`) that a learner program in any language must honour, so H5 tests the harness, not the learner's release path.
- **Failure scenario:** `runs/hw-check.bad.txt` shows H1 ✔, and R47 "bad fixture ✘ on H1, H2" fails. The controller then edits H1 into something artificial, or logs a deviation for a test bug. Đạt's own Go or TS solution ignores the undeclared slowness, H5 passes or fails at random, and the slide-43 compare-and-delete lesson is not checked.
- **Evidence:** `phase-04-widget-data-homework-driver.md:31`, `:33`, `:37`, `:39`, `:59`; `plan.md:109`.
- **Suggested fix:** Define H1 by the log, not the key: count of `BOOKED` lines plus the number of distinct owner tokens written to the booking key, recorded with `SET … GET` or `RPUSH l06:hw:writes`. Add `HW_HOLD_MS` and `HW_TTL_MS` to the homework contract as required env inputs. H5 runs round 11 with `HW_TTL_MS=50 HW_HOLD_MS=200` and checks that holder 2's token is still in the lock key after holder 1 releases.
