Cách chạy lệnh

Phải lọc dòng # vì redis-cli gửi chúng như một lệnh và trả ERR unknown command '#' (đã thử trên máy bạn). Vì thế khối lệnh trong guide đã bỏ sẵn dòng chú thích; file trong labs/ vẫn giữ chú thích tiếng Việt để bạn đọc.
  • File .sh: dán từng dòng vào Git Bash. Mỗi dòng là một lệnh trọn vẹn, không có heredoc hay if/for nhiều dòng. Mỗi region có một dòng set -u: shell dừng khi gặp biến chưa gán, nên gõ thiếu là lộ ngay. Dòng đó còn bật trong tab sau khi region chạy xong và có thể làm hỏng tab-completion của git (unbound variable khi bấm Tab): xong chặng thì gõ set +u hoặc mở tab mới.
  • DBX, kết nối ADVANCE_BE_REDIS (host 127.0.0.1, cổng 6379): dùng để duyệt khóa (kiểu, TTL, bộ nhớ) và gõ từng lệnh một. Thí nghiệm hai terminal (A và B)

Mở hai tab, mỗi tab một phiên redis-cli như trên, đặt tên A và B. Thứ tự luôn là:

  1. Chạy region …-reset (nằm trong file A) để đưa khóa của kịch bản về trạng thái đầu.
  2. Bắt đầu B. Lệnh đầu của B là BLPOP l06:barrier:<kịch bản> 5, nên B đứng chờ tối đa 5 giây. Khối .sh (Git Bash): dán cả khối B, các dòng sau tự đợi tới lượt. Khối .redis (redis-cli): chỉ dán dòng BLPOP của B; các dòng sau của B dán từng dòng theo bảng từng bước của chặng.
  3. Trong 5 giây đó, dán khối A. Lệnh đầu của A là RPUSH l06:barrier:<kịch bản> go, thả B chạy. Với khối .sh, các bước sleep nằm sẵn trong file và tính từ lúc này, nên nhịp giống lần đã ghi. Với khối .redis (dán vào redis-cli), không có sleep: dán từng dòng của A và B theo đúng thứ tự và nhịp ghi trong bảng từng bước. Dán cả khối B một lần thì các dòng sau xếp hàng sau BLPOP và chạy dồn ngay khi BLPOP trả về, nên thứ tự không còn giống lần đã ghi.

Nếu B in (nil) trước khi bạn kịp dán A, nghĩa là đã quá 5 giây: chạy lại từ bước 1.

Vì sao Redis nhanh, và vì sao một lệnh chậm làm đứng cả server

Mục tiêu: tự thấy Redis chạy mọi lệnh trên một luồng (I/O threads đang tắt), thấy một lệnh 2 giây bắt client khác đứng chờ, rồi đo thứ gì thật sự làm chậm: số vòng mạng, kích thước value, hay số lệnh.

LÀ GÌ?
Redis là kho dữ liệu trong RAM. Một vòng lặp epoll theo dõi mọi socket, còn một luồng chính chạy lần lượt từng lệnh của mọi client.
TẠI SAO?
Một luồng nên mỗi lệnh đã nguyên tử, không cần khóa bên trong. Cái giá: một lệnh chậm (KEYS *, xóa big key, Lua chạy lâu) chặn tất cả, kể cả kết nối mới.
KHI NÀO KHÔNG?
Đừng nghĩ "Redis nhanh nên gọi bao nhiêu cũng được": mười lệnh gửi lần lượt tốn mười vòng mạng, gộp lại (pipeline, MGET) mới nhanh. Không bao giờ quét cả keyspace trên production.
Tình huống · tối thứ sáu ở chuỗi F&B

7 giờ tối, 40 máy POS đang gọi Redis lấy giỏ hàng và giá món. Một bạn admin gõ KEYS * trên production "để xem có bao nhiêu khóa". Mọi máy POS đứng hình vài giây, log không có lỗi, CPU của app vẫn thấp. Lý do: Redis chỉ có một luồng chạy lệnh, và luồng đó đang bận với KEYS. Một kiểu dữ liệu, nhiều cách lưu: encoding, và câu hỏi Hash hay JSON

Mục tiêu: đọc được Redis đang lưu một khóa thế nào (OBJECT ENCODING, MEMORY USAGE), biết ngưỡng nào làm nó đổi cách lưu, và trả lời câu hỏi của slide 30 bằng số đo: hồ sơ khách nên là Hash hay chuỗi JSON, kể cả khi hai service sửa cùng lúc.

LÀ GÌ?
Mọi khóa nằm trong một hash table lớn (dict). Value của khóa có kiểu (String, Hash, Set, Sorted Set, List), và mỗi kiểu có encoding bên trong: dạng gọn khi nhỏ (listpack, intset, embstr), dạng đầy đủ khi lớn (hashtable, skiplist, raw).
TẠI SAO?
Encoding quyết định bộ nhớ và tốc độ. Một Hash còn gọn ở 512 trường, thêm đúng một trường là bộ nhớ nhảy vọt. Biết ngưỡng thì bạn thiết kế khóa vừa đủ nhỏ.
KHI NÀO KHÔNG?
Đừng cất object vào chuỗi JSON nếu nhiều nơi sửa từng trường: đọc, sửa, ghi đè cả chuỗi sẽ làm mất cập nhật của người khác. Và đừng nâng ngưỡng listpack thật cao chỉ để tiết kiệm RAM: listpack tìm tuần tự, phần tử càng nhiều càng chậm.

  • Cách 3: hashtable. Chỉ một trường desc dài hơn 64 byte (xem HSTRLEN) là cả Hash đổi encoding, và MEMORY USAGE nhảy hẳn lên so với cách 2. Bài học thiết kế: để mô tả dài ở khóa riêng (hoặc ở SQL), giữ Hash "nóng" chỉ gồm trường ngắn hay đọc.

Khóa hết hạn đi đâu, và khi RAM đầy thì Redis bỏ khóa nào

Mục tiêu: thấy bảng expires riêng, thấy khóa hết hạn vẫn chiếm RAM khi không ai đọc và chu kỳ nền dọn chúng ra sao, rồi cho một container riêng đầy bộ nhớ dưới 5 chính sách eviction và đếm khóa sống sót.

LÀ GÌ?
Khóa có TTL nằm ở hai bảng: bảng chính và expires. Khóa hết hạn bị xóa khi có người đọc (passive) hoặc bởi chu kỳ nền quét dần bảng expires (active). Chạm maxmemory thì chính sách eviction chọn bỏ khóa nào, hoặc từ chối ghi.
TẠI SAO?
Hết hạn chưa chắc đã trả RAM ngay. Chọn sai chính sách thì hoặc mất khóa quan trọng, hoặc POS không ghi được giỏ hàng.
KHI NÀO KHÔNG?
Đừng dùng TTL làm bộ hẹn giờ chính xác (hủy đơn sau 10 phút dùng Sorted Set, chặng 6). Đừng dùng allkeys-* cho Redis giữ thứ không được mất (idempotency, hàng đợi).

Cửa sổ khoảng một giây của everysec chỉ mở khi hệ điều hành sập hoặc mất điện. Máy này không đo kịch bản đó; đây là điều đọc từ tài liệu Redis. Muốn đóng cửa sổ thì appendfsync always (chậm hơn nhiều), hoặc để PostgreSQL giữ phần không được mất.

Delay task không xử lý trùng, xóa big key không làm Redis đứng

Mục tiêu: dựng hàng chờ trễ bằng ZSET, thấy hai poller ngây thơ cùng xử lý một đơn, sửa bằng script Lua nhận việc nguyên tử, rồi đo DEL và UNLINK trên hash một triệu field.

LÀ GÌ?
Delay task: ZSET, member là mã đơn, score là giờ đến hạn; poller lấy việc có score ≤ bây giờ. Big key: một khóa quá lớn, chuỗi dài hoặc collection rất nhiều phần tử.
TẠI SAO?
Hai instance hub là hai poller; đọc rồi mới xóa thì cả hai cùng thấy một đơn. DEL big key bắt luồng chính giải phóng bộ nhớ, mọi POS phải chờ.
KHI NÀO KHÔNG?
Cần retry có backoff, dead-letter thì dùng thư viện hàng đợi (BullMQ cũng chạy trên Redis). Đừng thay delay queue bằng TTL + keyspace notification: thông báo không được lưu, client rớt kết nối là mất.

-- "Bây giờ" lấy từ đồng hồ của Redis (TIME), không do client truyền vào.
local now = tonumber(redis.call('TIME')[1])
local due = redis.call('ZRANGE', KEYS[1], '-inf', now, 'BYSCORE', 'LIMIT', 0, 1)

  return nil -- chưa có việc nào đến hạn (hoặc người khác đã nhận mất)
end
redis.call('ZREM', KEYS[1], due[1])
redis.call('RPUSH', KEYS[2], due[1])

Replica trả giá cũ, slot và hashtag

Mục tiêu: tự cắt mạng giữa main và replica, thấy main vẫn nhận ghi còn replica vẫn trả giá cũ, rồi nối lại và xem hai bên khớp offset. Sau đó tính hash slot bằng tay, so với CLUSTER KEYSLOT, và dùng hashtag để hai khóa chạy chung một lệnh trên cluster.

LÀ GÌ?
Replica nhận bản sao các lệnh ghi của main theo kiểu bất đồng bộ: main trả OK cho client trước, gửi sang replica sau. Cluster chia 16384 hash slot cho các node; mỗi khóa thuộc một slot theo CRC16(khóa) mod 16384, hoặc theo phần nằm trong {…} nếu khóa có hashtag.
TẠI SAO?
Replica giúp đọc được nhiều hơn và có sẵn một bản dự phòng. Cluster giúp dữ liệu và lượt ghi vượt sức một node. Cả hai đổi lại một điều: có lúc dữ liệu giữa các node lệch nhau.
KHI NÀO KHÔNG?
Đừng đọc từ replica cho dữ liệu phải đúng ngay sau khi ghi: giá đang bán, tồn kho, khóa phân tán. Đừng bật cluster khi một node còn đủ sức: lệnh nhiều khóa bị giới hạn trong một slot và vận hành nặng hơn hẳn.

Tối thứ sáu, quản lý chuỗi đổi giá Trà đào trên hệ thống. Lệnh ghi vào Redis main trả OK. Sentinel theo dõi master và replica, làm service discovery. Khi master chết, các sentinel bầu một leader để chọn replica lên làm master và cho các replica khác theo master mới. Ưu: giải quyết failover. Nhược: dữ liệu lệch, tốn công vận hành, không scale được phần ghi.

Theo tài liệu redis.io (chưa đo ở đây): một master chỉ bị coi là chết khi đủ quorum sentinel cùng đồng ý, và failover cần đa số sentinel cho phép. Muốn thu hẹp cửa sổ mất ghi, master có thể đặt min-replicas-to-write để từ chối ghi khi không đủ replica còn nối.

-- Bài 06 · Chặng 8 — Lấy khóa VÀ nhận fencing token trong cùng một script (nguyên tử).
-- KEYS[1] = khóa, KEYS[2] = bộ đếm fencing token, ARGV[1] = token riêng của lần giữ khóa, ARGV[2] = TTL (ms).

Tùy chọn 5 phút · Redlock, nói thật

Redlock là thuật toán của antirez: lấy cùng một khóa trên N master Redis độc lập (thường là 5), coi là giữ được khi lấy xong ở đa số node trong thời gian ngắn hơn TTL. Mục đích là khóa vẫn sống khi một node Redis chết.

Phản biện của Martin Kleppmann ("How to do distributed locking", 2016): Redlock dựa vào giả định thời gian. Nó cần tiến trình không bị dừng quá lâu, mạng không trễ quá lâu, và đồng hồ các node không lệch quá nhiều. Khi giả định sai, hai client vẫn cùng tin mình giữ khóa, và Redlock không cấp fencing token nào để nơi lưu dữ liệu chặn người đến muộn. antirez đã viết bài trả lời; hai bên không thống nhất.

Bằng chứng ngay trên máy bạn: khi ghi lab này, đồng hồ máy ảo Docker chạy nhanh hơn Windows và bị chỉnh lùi theo đợt, nên có lần khóa PX 2000 sống lâu hơn dự kiến tính theo đồng hồ host. TTL đo bằng đồng hồ của server Redis, không phải của bạn. Thêm 4 node nữa không sửa được điều đó.

Kết luận dùng được: cần khóa để tránh làm trùng việc thì một Redis + SET NX PX + compare-and-delete là đủ. Cần đúng dữ liệu thì thêm fencing token hoặc điều kiện version ở nơi ghi (kịch bản 5). Redlock tốn 5 node mà không cho thêm cái nào trong hai thứ đó.

Token bucket, Idempotency-Key và checklist slide 41

Mục tiêu: đo vì sao token bucket kiểu "GET, tính trong code, SET" cho lọt hai request từ một token, rồi chạy bản Lua nguyên tử đúng như FR-M2-05 cần (30 request, sức chứa 10 → 20 bị từ chối kèm thời gian chờ). Sau đó chạy bốn trạng thái của Idempotency-Key cho FR-M2-02 và Boss Challenge 2, và đi lại checklist slide 41 với số đã đo ở các chặng trước.

LÀ GÌ?
Token bucket: mỗi storeId có một xô chứa tối đa capacity token, được nạp lại rate token mỗi giây; mỗi request lấy 1 token, hết token thì trả 429. Idempotency-Key: client gửi kèm một khóa; server nhớ khóa đó cùng hash của body để request gửi lại không bị xử lý hai lần.
TẠI SAO?
Cả hai là "đọc → quyết định → ghi" trên dữ liệu dùng chung. Làm bằng nhiều lệnh từ app thì hai request chen vào giữa nhau. Gói vào một script Lua thì Redis chạy liền một mạch, không ai chen vào được.
KHI NÀO KHÔNG?
Giới hạn tốc độ chỉ cần gần đúng trên một instance thì bộ đếm trong bộ nhớ là đủ. Idempotency-Key không thay được khóa dòng: hai request khác khóa cùng hủy một hợp đồng vẫn tranh nhau, phần đó là việc của FOR UPDATE hoặc UPDATE … WHERE có điều kiện (Bài 14).

local tokens = tonumber(redis.call('HGET', KEYS[1], 'tokens'))
local ts = tonumber(redis.call('HGET', KEYS[1], 'ts'))
if tokens == nil then
  tokens = cap -- bucket mới: đầy
  ts = now
end
-- Đồng hồ server có thể bị chỉnh lùi (chặng 8 đã thấy trên máy ảo Docker): khi đó now < ts, không được nạp số âm.
local elapsed = math.max(0, now - ts)
tokens = math.min(cap, tokens + elapsed / 1000 * rate)
local allowed, retry = 0, 0
if tokens >= 1 then
  allowed = 1
  tokens = tokens - 1
else
  retry = math.ceil((1 - tokens) / rate) * 1000
end
redis.call('HSET', KEYS[1], 'tokens', tokens, 'ts', now)
-- Bucket không ai gọi tới thì tự hết hạn sau thời gian nạp đầy lại.
redis.call('PEXPIRE', KEYS[1], math.ceil(cap / rate * 1000))
return {allowed, math.floor(tokens), retry}

-- Bài 06 · Chặng 9 — Bắt đầu một request có Idempotency-Key (OmniPOS FR-M2-02, tiếp Bài 01).
-- KEYS[1] = bản ghi của key (Hash: hash, status, resp), ARGV[1] = hash của body request, ARGV[2] = TTL (giây).
-- Trả:
--   NEW          lần đầu thấy key: đã giữ chỗ với status IN_PROGRESS, app được phép xử lý
--   IN_PROGRESS  request trùng tới khi bản đầu còn đang chạy: app trả 409, không xử lý lại
--   {DONE, resp} đã xử lý xong: app trả lại đúng response đã lưu
--   MISMATCH     cùng key nhưng body khác: app trả 422
local h = redis.call('HGET', KEYS[1], 'hash')
if not h then
  redis.call('HSET', KEYS[1], 'hash', ARGV[1], 'status', 'IN_PROGRESS')
  redis.call('EXPIRE', KEYS[1], ARGV[2])
  return 'NEW'
end
if h ~= ARGV[1] then
  return 'MISMATCH'
end
local st = redis.call('HGET', KEYS[1], 'status')
if st == 'DONE' then
  return {'DONE', redis.call('HGET', KEYS[1], 'resp')}
end
return st

import { randomUUID } from 'node:crypto';

const URL = process.env.REDIS_URL ?? 'redis://127.0.0.1:6379'; // 127.0.0.1, không dùng localhost (Windows có thể thử ::1 trước)
const TTL_MS = Number(process.env.HW_TTL_MS ?? 2000);
const HOLD_MS = Number(process.env.HOLD_MS ?? 100);
const LOCK = 'l06:hw:lock:FA634:A34_S012C';
const BOOKINGS = 'l06:hw:bookings:FA634';
const LOG = 'l06:hw:log';
// Trả khóa kiểu compare-and-delete: chỉ xóa khi khóa vẫn mang token của mình (giống lua/lock-release.lua).
const RELEASE = "if redis.call('GET', KEYS[1]) == ARGV[1] then return redis.call('DEL', KEYS[1]) end return 0";
const sleep = (ms) => new Promise((r) => setTimeout(r, ms));

// Mỗi request một kết nối riêng, như 2 instance API khác nhau.
async function connect() {
  const c = createClient({ url: URL });
  c.on('error', (err) => console.error('redis error:', err.message)); // bắt buộc có listener 'error'
  await c.connect();
  return c;
}

async function book(client, name) {
  const token = randomUUID(); // token riêng của request này
  // SET NX PX: chỉ một request lấy được khóa; khóa tự hết hạn sau TTL_MS nếu request chết giữa chừng.
  const ok = await client.set(LOCK, token, { condition: 'NX', expiration: { type: 'PX', value: TTL_MS } });
  if (ok !== 'OK') {
    await client.rPush(LOG, `REJECTED ${token}`);
    return `${name}: ghế đang có người giữ → từ chối`;
  }
  try {
    await sleep(HOLD_MS); // giả lập kiểm tra ghế, tính tiền...
    await client.rPush(BOOKINGS, `A34_S012C ${token}`);
    await client.rPush(LOG, `BOOKED ${token}`);
    return `${name}: đặt được ghế`;
  } finally {
    // Trả khóa trong finally: lỗi giữa chừng cũng không để khóa treo tới hết TTL.
    await client.eval(RELEASE, { keys: [LOCK], arguments: [token] });
  }
}

try {

} finally {

}

import { Injectable, OnModuleDestroy, OnModuleInit } from '@nestjs/common';
import { createClient, RedisClientType } from 'redis';

const redis: RedisClientType = createClient({ url: 'redis://127.0.0.1:6379' });

@Injectable()
export class MenuCacheService implements OnModuleInit, OnModuleDestroy {
  async onModuleInit() {
    await redis.connect();
  }

  async onModuleDestroy() {
    await redis.close();
  }

  // Lưu menu của cửa hàng vào cache.
  async saveMenu(storeId: string, menuJson: string) {
    await redis.set(`menu:${storeId}`, menuJson);
  }

  // Admin sửa một món → xóa cache menu của mọi cửa hàng (gọi trong request của admin).
  async invalidateAllMenus() {
    const keys = await redis.keys('menu:*');
    if (keys.length) await redis.del(keys);
  }

  // Trang chủ hiện giá của 20 món.
  async getPrices(itemIds: string[]) {
    const prices: (string | null)[] = [];
    for (const id of itemIds) {
      prices.push(await redis.get(`price:${id}`));
    }
    return prices;
  }

  // Đếm lượt xem menu của cửa hàng.
  async countView(storeId: string) {
    const n = Number((await redis.get(`views:${storeId}`)) ?? 0);
    await redis.set(`views:${storeId}`, String(n + 1));
  }

  // Số lượng một món trong giỏ (giỏ của khách sỉ có thể tới vài chục nghìn dòng).
  async getCartQty(userId: string, itemId: string) {
    const cart = await redis.hGetAll(`cart:${userId}`);
    return Number(cart[itemId] ?? 0);
  }
}

@Injectable()
export class SeatLockService {
  // Giữ ghế 2 giây trong lúc thanh toán; token là chuỗi ngẫu nhiên của request.
  async lockSeat(flight: string, seat: string, token: string): Promise<boolean> {
    const ok = await redis.set(`lock:${flight}:${seat}`, token, {
      condition: 'NX',
      expiration: { type: 'PX', value: 2000 },
    });
    return ok === 'OK';
  }

  // Thanh toán xong thì trả ghế.
  async releaseSeat(flight: string, seat: string, token: string) {
    await redis.del(`lock:${flight}:${seat}`);
  }
}

Quy tắc dùng Redis

  1. Không chạy lệnh O(N) trên keyspace hay key lớn ở đường request: SCAN thay KEYS, UNLINK thay DEL cho key lớn (chặng 1, 6).
  2. Gom lượt mạng: MGET/pipeline thay cho N lệnh nối tiếp (chặng 1).
  3. Đọc-sửa-ghi phải nguyên tử: lệnh có sẵn (INCR, HINCRBY) hoặc Lua (chặng 2, 5, 6, 9).
  4. Mọi khóa cache có TTL kèm jitter; chọn maxmemory-policy theo vai trò của instance (chặng 3, Bài 02).
  5. Biết mình mất gì khi sập: RDB mất từ ảnh chụp cuối, AOF everysec chỉ mất khi hệ điều hành sập (chặng 4).
  6. Khóa phân tán: SET NX PX + token, nhả bằng compare-and-delete, fencing token cấp cùng script với lệnh lấy khóa và được kiểm ở chỗ ghi cuối (chặng 8).
  7. Replica có thể trả dữ liệu cũ; trong Cluster, khóa dùng chung lệnh phải chung hashtag (chặng 7).
