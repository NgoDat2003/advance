Bức Tranh Toàn Cảnh 4 Tầng Lưu Trữ & Bộ Nhớ Đệm

Hành trình của 1 Request từ Điện thoại/Trình duyệt của khách → NestJS API → Redis → PostgreSQL Buffer Pool → Ổ cứng DB

TẦNG 1 · Thiết bị người dùng
Browser Cache / TanStack Query
📍 Nằm trên: RAM của từng chiếc điện thoại / laptop khách hàng
  • Ai dùng được? Chỉ 1 mình máy đó dùng. Máy Quán 1 không nhìn thấy RAM của Máy Quán 2.
  • Lưu cái gì? Kết quả JSON mà máy đó vừa tải về trong vài giây/phút trước (staleTime).
  • Tốc độ: 0 ms (Bấm qua lại giữa các tab không tốn 1 gói tin mạng nào).
❓ Tại sao có Tầng 1 rồi vẫn cần Redis? Khi 10.000 người mới cùng mở app lúc 12h trưa, RAM của cả 10.000 máy đều trống → cả 10.000 máy vẫn bắn HTTP lên Server!
⬇ Khi máy khách chưa có Cache (hoặc hết hạn) → Bắn HTTP Request qua Internet lên Backend API ⬇
Trạm Điều Phối
NestJS Backend API
📍 Nằm trên: Server Backend (Cổng 3101)
  • Nhận HTTP Request từ 10.000 máy khách.
  • Chiến lược đọc (Cache-Aside): Hỏi Tầng 2 (Redis) trước. Có thì trả về ngay (99%). Không có mới xuống Tầng 3 & 4 (PostgreSQL) lấy rồi đút ngược vào Redis cho người sau ăn sẵn.
💡 Vai trò: Bản thân NestJS không giữ dữ liệu (Stateless) để có thể nhân bản thành 5–10 con API chạy song song.
⬇ Bước 1: Hỏi Tầng 2 (Redis) trước (~0.1 ms) · Nếu Redis chưa có (Cache Miss) hoặc cần Ghi Tiền thì mới xuống Tầng 3 & 4 ⬇
TẦNG 2 · RAM Hệ Thống Backend
Redis Server (System Cache)
📍 Nằm trên: RAM của Server trung tâm (Cổng 6379)
  • Ai dùng được? Tất cả 10.000 người dùng chung! Người số 1 mở app làm ấm Redis → 9.999 người sau lấy ra ăn sẵn!
  • Lưu cái gì? Món ăn đã nấu chín (Cục JSON thực đơn đã JOIN sẵn, Hash thông tin quán, Bộ đếm Rate Limit, Khóa phân tán).
  • Tốc độ: ~0.1 ms · Gánh 100.000+ req/s chỉ bằng 1 luồng chính.
❓ Tại sao có Redis rồi vẫn cần PostgreSQL? RAM đắt (chỉ lưu dữ liệu nóng có thời hạn TTL), và Redis không có SQL JOIN, CHECK hay sổ cái ACID vĩnh viễn như DB.
⬇ Chỉ 1% lượt đọc bị trượt Redis (Cache Miss) + các giao dịch Tiền Bạc (Chuyển ví, Nhận Voucher) mới đi xuống PostgreSQL ⬇
TẦNG 3 · RAM Nội Bộ Của Database
PostgreSQL Buffer Pool (shared_buffers)
📍 Nằm trên: RAM của Server PostgreSQL (Cổng 5434)
  • Lưu cái gì? Nguyên liệu thô — các trang bảng và trang B-Tree Index kích thước 8 KB hay dùng nhất (chính là Buffers: shared hit Đạt học ở Bài 03).
  • Tác dụng: Giúp PostgreSQL đọc/sửa dòng ví ngay trên RAM của DB mà không phải thò đầu xuống ổ cứng đọc từng trang.
❓ Câu hỏi triệu đô: Tầng 3 cũng là RAM, sao vẫn cần Tầng 2 (Redis)? Xem bảng so sánh "Món nấu chín vs Nguyên liệu thô" ngay bên dưới!
⬇ Đọc trang chưa có trên RAM (shared read) & Ghi vĩnh viễn sổ cái xuống đĩa (WAL + Heap) ⬇
TẦNG 4 · Ổ Cứng Vật Lý (Kho Bạc Gốc)
PostgreSQL Heap + Index + WAL (SSD / NVMe)
📍 Nằm trên: Ổ cứng vật lý của Server Database
  • Vai trò tối thượng: Source of Truth (Kho bạc cuối cùng). Cúp điện cả tòa nhà thì số dư 301 ví (wallets) và bút toán (ledger_entries) vẫn còn nguyên vẹn 100%.
  • Tốc độ: Chậm nhất trong 4 tầng → nhờ Tầng 1, 2, 3 chắn đỡ 99% lượt đọc nên Tầng 4 rảnh tay khóa FOR UPDATE và ghi tiền chuẩn xác!
✅ Kết luận 1 câu: Tầng 1, 2, 3 dùng RAM để tăng tốc; Tầng 4 dùng ổ cứng để giữ tiền không bao giờ mất!

🔥 Điểm Hay Bị Nhầm Nhất: Cùng là RAM trên Server, nhưng Tầng 2 (Redis) khác Tầng 3 (DB Buffer Pool) chỗ nào?

🍱 Tầng 2 — Redis: "Hộp Cơm Đã Nấu Chín Sẵn"

Khi khách hỏi "Top 10 món bán chạy kèm tên quán và giá":

• Trong Redis lưu sẵn cục kết quả cuối cùng tại key bestsellers:top10.
• API chỉ gõ đúng 1 lệnh GET bestsellers:top10 → Bốc ra trả luôn trong 1 bước (O(1)), tốn 0% CPU của Database!

🥩 Tầng 3 — DB Buffer Pool: "Tủ Lạnh Chứa Thịt Sống, Rau Sống"

Nếu không có Redis mà bắt PostgreSQL trả lời câu hỏi trên từ Buffer Pool:

• Dù các trang 8KB của bảng orders, products, stores đã nằm trên RAM của DB, nhưng mỗi lần khách hỏi, CPU của PostgreSQL vẫn phải đứng nấu lại từ đầu: Dịch câu SQL → Duyệt B-Tree → Kiểm tra MVCC (xmin/xmax) → JOIN 3 bảng → GROUP BY + ORDER BY!
• 10.000 người hỏi cùng lúc = 10.000 lần bắt đầu bếp DB nấu lại từ đầu → Cháy 100% CPU Database!
