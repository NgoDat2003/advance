## 5. Scouted facts to verify or use (controller observations; verify with labs before quoting)

The deck describes MySQL/InnoDB; the learner's lab and production DB is PostgreSQL 16.

1. Slide 7: PG accepts `READ UNCOMMITTED` but runs it as Read Committed — no dirty reads at any level in PG. InnoDB RU does allow dirty reads.
2. Slide 8: PG's default is RC (correct). Each statement takes a new snapshot, so non-repeatable reads and phantoms are possible. An UPDATE that hits a row updated by a concurrent transaction waits, then re-checks the row's newest version (EvalPlanQual): `SET qty = qty - 1` stays correct, while an application read-modify-write (SELECT, compute in the app, UPDATE with the computed value) loses updates.
3. Slide 9: PG RR is snapshot isolation with the snapshot taken at the first statement (not at BEGIN): no non-repeatable reads **and no phantoms** (stronger than the SQL standard minimum). A concurrent update of the same row gives `ERROR 40001 could not serialize access due to concurrent update` (first updater wins), so the app-level lost update is caught. **Write skew is still possible** (roadmap Day 03). InnoDB RR: consistent reads use a snapshot, but locking reads and UPDATE read the latest version ("current read") and take next-key/gap locks.
4. Slide 10: "Serializable places a lock on every row it reads" is InnoDB (SERIALIZABLE turns plain SELECT into `SELECT … FOR SHARE` when autocommit is off). PG uses SSI: non-blocking SIRead predicate locks; it detects dangerous read/write dependency structures and aborts one transaction with `40001 could not serialize access due to read/write dependencies among transactions`; the application must retry. The cost is retries, false positives and predicate-lock memory, not blocking.
5. Slide 12: the WAL principle holds for both. PG: WAL in `pg_wal`, LSN via `pg_current_wal_lsn()`, `pg_wal_lsn_diff()`, `EXPLAIN (ANALYZE, WAL)`, `pg_stat_wal`; commit = WAL flush when `synchronous_commit = on`; data pages are written later by the checkpointer/bgwriter; `full_page_writes` is the torn-page protection (InnoDB uses the doublewrite buffer). `synchronous_commit = off` trades losing the last few committed transactions on a crash for commit latency, without corruption.
6. Slides 13–14: PG has no undo log. UPDATE writes a new tuple version into the heap (`xmin` = creating xid, `xmax` = deleting/locking xid); the old version stays as a dead tuple until VACUUM; ROLLBACK only marks the xid aborted in `pg_xact` (instant, no undo work), while InnoDB rollback replays undo (slow for big transactions). Visibility follows snapshot rules (`pg_current_snapshot()`, `pg_current_xact_id()` / `txid_current()`). Lesson 3 Lab 03 already showed ctid moves and HOT updates — build on it, do not repeat it.
7. Slide 15 is empty: the guide must supply "MVCC in Postgres" (the core of the lesson for a PG learner).
8. Slide 16: HLL is an InnoDB metric (numbers from *Efficient MySQL Performance*, not measurable here). PG analog: dead tuples that VACUUM cannot remove because an old snapshot holds back the xmin horizon — `pg_stat_user_tables.n_dead_tup`, `VACUUM (VERBOSE)` "dead but not yet removable", `pg_stat_activity.backend_xmin`, oldest `xact_start`; replication slots and prepared transactions also hold the horizon.
9. Slide 18: in PG a huge UPDATE/DELETE produces a large WAL volume, many dead tuples (bloat), long-held row locks and replication lag; batching (commit per chunk) is the usual fix — measurable with WAL bytes and dead tuples.
10. Slides 19–21: PG shows long/stalled/abandoned transactions as `state = 'idle in transaction'` in `pg_stat_activity`; guards: `idle_in_transaction_session_timeout` (currently 0 = off), `statement_timeout`, `lock_timeout`, `idle_session_timeout` (PG14+); kill with `pg_terminate_backend()`. Gap locks (slide 20) do not exist in PG. Typical app causes: external HTTP/file I/O inside a DB transaction; a TypeORM `QueryRunner` not released in `finally`.
11. Slide 22: MySQL `SET TRANSACTION` (no scope keyword) = next transaction only. PG: `SET TRANSACTION ISOLATION LEVEL …` only works inside a transaction block before its first query and applies to the current transaction (outside a block it only warns); the session default is set via `SET SESSION CHARACTERISTICS AS TRANSACTION …` or `default_transaction_isolation`; shortcut `BEGIN ISOLATION LEVEL SERIALIZABLE`. PG also autocommits every statement outside `BEGIN`; GUI clients (DBeaver/pgAdmin/DBX) have their own auto-commit toggle, which matters for manual two-session labs.
12. Slide 23: in PG writers still take row locks (an UPDATE blocks a concurrent UPDATE/DELETE of the same row), but readers never block writers and writers never block readers. Locking itself is lesson 14.
13. PG-specific behaviour outside the slides worth teaching: an error inside a transaction gives `25P02 current transaction is aborted, commands ignored until end of transaction block` (MySQL keeps going); SAVEPOINT for partial rollback; DDL is transactional (MySQL commits implicitly); sequences are not rolled back (gaps in ids).
14. Expected PG 16 anomaly matrix (verify, do not assume): dirty read — never; non-repeatable read — RC yes, RR/SER no; phantom — RC yes, RR/SER no; app lost update — RC yes, RR/SER give 40001; write skew — RC yes, RR yes, SER gives 40001.
15. NestJS + TypeORM: `dataSource.transaction('SERIALIZABLE', async (manager) => …)`; `queryRunner.startTransaction('REPEATABLE READ')` / `commitTransaction()` / `rollbackTransaction()` / `release()` in `finally`; common bugs: using the injected repository (global manager) inside the callback instead of `manager` (the query runs outside the transaction), slow external calls inside the transaction, no retry on 40001/40P01, a leaked QueryRunner leaving the session idle in transaction. Verify API names against the TypeORM 0.3 docs before quoting.
