Ví âm −20: ai thật sự chặn được?

Mục tiêu: tái hiện đúng con số −20 của slide 2, rồi chỉ ra cơ chế nào chặn được nó và cơ chế nào không.

LÀ GÌ?
Race condition: hai request cùng kiểm tra "đủ tiền" trên số dư cũ, rồi cùng trừ.
TẠI SAO?
Kiểm tra và trừ là hai bước. Giữa hai bước, request kia chen vào.
KHI NÀO KHÔNG?
Đừng tự chế khóa trong app khi một câu UPDATE … WHERE balance >= 40 đã đủ.

Slide 2 kết luận "ví A = −20". Con số này chỉ ra khi có đủ hai điều kiện: kiểm tra trên số dư cũ (cả hai đọc 50), và trừ tương đối balance = balance - 40. Lab 14.01 chạy 5 cách viết trên cùng dữ liệu để bạn so.

Đo trên máy bạn · Lab 14.01
  • A. Kiểm tra cũ + trừ tương đối: B chờ khóa dòng của A, rồi trừ 40 trên số dư mới 20 → ví A = -20, tổng vẫn 50.
  • B. App tự tính rồi ghi tuyệt đối SET balance = 10: ví A = 10, tổng = 80 (in thêm 30 tiền).
  • C. SELECT … FOR UPDATE rồi mới kiểm tra: B chờ, đọc 20, từ chối.
  • D. UPDATE … AND balance >= 40: B được rowCount 0, ví A = 20.
  • E. CHECK (balance >= 0): B nhận 23514, ví A = 20.

Cả 5 cách B đều chờ Lock/transactionid. Khóa dòng của UPDATE luôn có; nó chỉ không kiểm tra hộ bạn.

S/X → 4 chế độ khóa dòng; khóa nằm ở xmax

Mục tiêu: đổi mô hình S/X của slide 3 sang 4 chế độ khóa dòng của PG, và tự liệt kê ai đang giữ khóa nào.

LÀ GÌ?
PG có 4 chế độ khóa dòng, từ nhẹ đến nặng: FOR KEY SHARE, FOR SHARE, FOR NO KEY UPDATE, FOR UPDATE.
TẠI SAO?
Tách nhỏ để INSERT dòng con (kiểm tra FK) không phải chờ một UPDATE cột thường trên dòng cha.
KHI NÀO KHÔNG?
SELECT thường không xin khóa dòng: nó đọc snapshot nên không chờ người đang sửa dòng (vẫn lấy AccessShareLock mức bảng — chặng 3).
Slide 3 · Lab 14.02 Cần sửa
Slide nói

Chỉ có S và X; định nghĩa "Exclusive (Update): Lock to read and write", tức giữ X thì người khác không đọc được.

PG 16 đo được

A giữ FOR UPDATE, B SELECT thường trả về 1 dòng ngay, không chờ. Có 4 chế độ, ma trận đo khớp tài liệu 16/16 ô.

MySQL 8.4 · không đo trên máy này

Trên InnoDB, SELECT thường cũng không chờ khóa X: đó là "consistent nonlocking read". S/X chỉ áp cho locking read (FOR SHARE / FOR UPDATE). Nguồn: MySQL 8.4 · Consistent Nonlocking Reads, Locking Reads.

InnoDB S/X · không đo trên máy này

S tương thích S; X xung đột với cả S và X. Gần đúng: S ≈ FOR SHARE, X ≈ FOR UPDATE. Hai mode giữa (KEY SHARE, NO KEY UPDATE) là phần riêng của PG. Nguồn: MySQL 8.4 · Shared and Exclusive Locks.

Câu lệnh nào lấy mode nào: UPDATE cột thường lấy FOR NO KEY UPDATE. UPDATE cột khóa chính (hoặc cột có unique index dùng được cho FK) hoặc DELETE lấy FOR UPDATE. INSERT dòng con kiểm tra FK lấy FOR KEY SHARE trên dòng cha.

Lab 14.02 C đo đúng điều đó trên bảng chuyến bay. UPDATE seats thì INSERT vé con chạy ngay. UPDATE id thì INSERT vé con phải chờ.

Khóa dòng nằm ở đâu?

PG không giữ danh sách từng khóa dòng trong bộ nhớ chung. Nó ghi xid của người khóa vào cột ẩn xmax của tuple. Vì vậy pg_locks của người giữ không có dòng tuple nào.

Khóa bảng và hàng đợi DDL làm treo cả SELECT

Mục tiêu: hiểu vì sao một ALTER TABLE đang chờ có thể làm treo mọi SELECT, và chặn sự cố đó bằng lock_timeout.

LÀ GÌ?
Mỗi câu lệnh lấy một khóa bảng: SELECT → AccessShareLock, SELECT FOR UPDATE → RowShareLock, UPDATE → RowExclusiveLock, ALTER TABLE … ADD COLUMN (và đa số dạng ALTER) → AccessExclusiveLock.
TẠI SAO?
AccessExclusiveLock xung đột với mọi mode. ALTER xếp hàng, và mọi câu đến sau phải xếp sau nó.
KHI NÀO KHÔNG?
Đừng chạy migration khi có transaction dài đang mở, và đừng chạy migration không có lock_timeout.
Slide 6 · Lab 14.03 MySQL đúng, PG khác
Slide nói

Phân loại khóa của MySQL: global, table, intention, AUTO-INC, rồi các loại khóa dòng.

PG 16 đo được

PG có 8 mode khóa bảng (tài liệu §13.3.1), không có global hay AUTO-INC lock riêng; vai trò intention lock (IS/IX) do RowShareLock/RowExclusiveLock đảm nhận. Lab đo: UPDATE → RowExclusiveLock, SELECT … FOR UPDATE → RowShareLock, SELECT thường → AccessShareLock.

MySQL 8.4 · không đo trên máy này

InnoDB có intention lock (IS/IX) ở mức bảng trước khi khóa dòng, AUTO-INC lock cho cột tự tăng, và global lock kiểu FLUSH TABLES WITH READ LOCK. Nguồn: MySQL 8.4 · Intention Locks, AUTO-INC Locks, FLUSH TABLES WITH READ LOCK.

Sự cố thật: một báo cáo mở transaction rồi để đó. Bạn chạy migration ALTER TABLE. ALTER chờ báo cáo, còn mọi API SELECT bảng đó chờ ALTER.

Prisma 7 drill: rà một BookingService do AI viết

Đây là code NestJS + Prisma 7 giống dự án quan-ly-hop-dong của bạn. Nó chạy được khi chỉ có 1 người dùng. Tìm 6 lỗi khóa trước khi mở đáp án; mỗi lỗi đã có một lab đo trong bài.

// booking.service.ts — bản nháp AI (NestJS + Prisma 7, adapter-pg)
@Injectable()
export class BookingService {
  constructor(
    private readonly prisma: PrismaService,
    private readonly payment: PaymentGateway,
  ) {}

  async bookRoundTrip(legs: { flightId: number; version: number }[], passenger: string) {
    const first = await this.prisma.flight.findUnique({ where: { id: legs[0].flightId } });
    if (!first || first.seats <= 0) throw new ConflictException('Hết ghế');

    return this.prisma.$transaction(async (tx) => {
      const ids = legs.map((l) => l.flightId);
      await tx.$queryRaw`SELECT id FROM flights WHERE id = ANY(${ids}) FOR UPDATE`;

      for (const leg of legs) {
        await tx.flight.updateMany({
          where: { id: leg.flightId, version: leg.version },
          data: { seats: { decrement: 1 }, version: { increment: 1 } },
        });
      }

      const booking = await this.prisma.booking.create({
        data: { flightId: legs[0].flightId, passenger },
      });
      await this.payment.charge(booking.id);          // HTTP sang cổng thanh toán
      return booking;
    });
  }

  async bookWithRetry(legs: { flightId: number; version: number }[], passenger: string) {
    for (let attempt = 1; ; attempt++) {
      try {
        return await this.bookRoundTrip(legs, passenger);
      } catch (e) {
        if (e?.code !== 'P2034' || attempt === 3) throw e;
      }
    }
  }
}
Đáp án 1 · vùng: kiểm tra ghế ở đầu hàm

Lỗi: findUnique và if (seats <= 0) chạy trước khi mở transaction và không khóa gì. Hai request cùng thấy còn ghế, rồi cùng trừ. Đây là TOCTOU, giống Lab 14.01 A (ví −20) và kịch bản s1 (3 vé cho 2 ghế).

Sửa: kiểm tra bên trong transaction, sau khi khóa; hoặc gộp kiểm tra vào chính câu ghi:

const { count } = await tx.flight.updateMany({
  where: { id: flightId, seats: { gt: 0 } },
  data: { seats: { decrement: 1 } },
});

Đáp án 2 · vùng: tạo vé (booking.create)

Lỗi: this.prisma.booking.create lấy một kết nối khác trong pool, nằm ngoài transaction. Nếu transaction rollback, vé vẫn còn.

Tệ hơn: INSERT vé kiểm tra FK, cần FOR KEY SHARE trên dòng chuyến bay. Transaction đang giữ FOR UPDATE trên đúng dòng đó (từ $queryRaw). Ma trận Lab 14.02 đo ô UPDATE × KEY SHARE = 55P03, và Lab 14.02 C đo INSERT con phải chờ. Kết nối ngoài chờ transaction, transaction chờ lệnh await của chính nó: PG không thấy vòng này, nên request treo tới khi hết timeout. (Suy ra từ Lab 14.02, chưa chạy bằng Prisma.)

Sửa: trong callback chỉ dùng tx: tx.booking.create(…).

Đáp án 3 · vùng: câu $queryRaw khóa các chuyến

Lỗi: thứ tự khóa do plan quyết định. Bản nháp Phần C đo được: cùng input [1, 2], Seq Scan khóa VN456 → VN123, Index Scan khóa VN123 → VN456. Hai request khác plan khóa ngược nhau → 40P01 (kịch bản s6). Sắp xếp mảng ids trong JS cũng không đủ.

Sửa: để SQL quyết định thứ tự, như M2: LockRows nằm trên nút tạo thứ tự của ORDER BY (Sort như Lab 14.05 D trên bảng 10 dòng, hoặc Index Scan theo id trên bảng lớn).

await tx.$queryRaw`SELECT id FROM flights WHERE id = ANY(${ids}) ORDER BY id FOR UPDATE`;
Đáp án 4 · vùng: vòng for trừ ghế

Lỗi: updateMany trả { count } và không bao giờ ném lỗi khi 0 dòng khớp. Version cũ → sửa 0 dòng, nhưng code vẫn tạo vé. Bản nháp Phần C đo đúng triệu chứng này: "vé ma" (ghế không đổi, số vé tăng). (Nếu dùng update với where không khớp thì Prisma ném P2025.)

Sửa:

  where: { id: leg.flightId, version: leg.version },
  data: { seats: { decrement: 1 }, version: { increment: 1 } },

Đáp án 5 · vùng: bookWithRetry

Lỗi: vòng retry chỉ bắt P2034. Mã này áp dụng cho truy vấn model (tx.flight.updateMany…): trên @prisma/adapter-pg 7.9.0 (đúng bản trong pnpm-lock.yaml của bạn) nó phủ 40001 nhưng không phủ 40P01; từ 7.10.0 mới phủ cả 40P01. Còn lỗi từ $queryRaw/$executeRaw, tức chính câu FOR UPDATE đang chờ khóa, tới dạng P2010 kèm SQLSTATE trong message, ở cả 7.9 lẫn 7.10. Vậy vòng retry bỏ sót đúng lỗi chặng 5 dạy, và chỉ nâng cấp thì chưa đủ.

Sửa: điều kiện chính là SQLSTATE 40P01/40001 trong lỗi; P2034 chỉ là điều kiện phụ. Đường raw → P2010 mới đọc từ mã nguồn runtime 7.9.0, chưa kiểm chứng trên 7.9 của bạn, nên hàm dưới bắt rộng:

function isRetryable(e: unknown): boolean {
  const err = e as { code?: string; meta?: unknown; message?: string };
  const raw = JSON.stringify(err?.meta ?? {}) + String(err?.message ?? '');
  if (raw.includes('40P01') || raw.includes('40001')) return true; // chính: SQLSTATE (P2010 từ $queryRaw)
  return err?.code === 'P2034';                                   // phụ: truy vấn model (40001; 40P01 từ 7.10.0)
}
// Thử lại CẢ $transaction (tối đa 3 lần, nghỉ ngẫu nhiên 20–100 ms giữa các lần).
Đáp án 6 · vùng: payment.charge

Lỗi: trong lúc chờ HTTP, transaction vẫn giữ khóa dòng chuyến bay; mọi người đặt cùng chuyến xếp hàng như dòng nóng Lab 14.08. Mặc định $transaction có maxWait 2000 ms và timeout 5000 ms. Cổng chậm hơn 5 s thì transaction bị hủy, nhưng tiền đã bị trừ.

Sửa: transaction ngắn giữ ghế (trạng thái PENDING) → COMMIT → gọi thanh toán ngoài transaction → transaction ngắn thứ hai xác nhận hoặc trả ghế. Hoặc ghi outbox trong transaction và để worker gọi HTTP.
