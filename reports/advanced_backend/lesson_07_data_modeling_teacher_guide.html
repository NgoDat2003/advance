Cách chạy một region trong DBX

Mỗi file chia thành nhiều region, mở bằng dòng -- #region tên · tiêu đề và đóng bằng -- #endregion. Bôi đen từ dòng mở tới dòng đóng → Run Selection. Tab để chế độ auto-commit; các chỗ cần transaction đã có sẵn BEGIN … COMMIT/ROLLBACK trong SQL.

  • Dòng đầu mỗi region là SET search_path = lab07_modeling;. Lý do: DB của bạn đặt mặc định search_path = lab03_indexing, public (kiểm tra C08), thiếu dòng này thì bảng sẽ bị tạo nhầm sang schema của Bài 3.

Làm mẫu · OmniPOS: đơn hàng và thanh toán
  1. Analysis. Use case: khách tạo đơn rồi thanh toán; khách ủng hộ (donate) mà không mua gì. Access pattern: tra đơn theo mã, xem các khoản thanh toán của một đơn. Field thô: mã đơn, trạng thái đơn, tổng tiền, loại giao dịch, số tiền, trạng thái giao dịch, thời điểm tạo.
  2. Data modeling. Gom field theo "thứ gì có vòng đời riêng": đơn hàng (NEW → PAID / CANCELLED) và giao dịch (PENDING → SUCCESS / FAILED). Hai entity, khóa chính bigint identity, nối bằng order_id nằm ở bảng giao dịch (lý do ở slide 12, chặng 3).
  3. Data integrity. Mỗi luật nghiệp vụ thành một ràng buộc: CHECK cho trạng thái, total >= 0, "đơn thì có order_id, donate thì không", và index cho cột order_id.

Mở labs/lesson-07-data-modeling/01-design-erd.sql trong DBX (tab ADVANCE_BE_LAB), bôi đen region erd → Run Selection.

-- #region erd · Hai entity Order và Payment theo table template (slide 7, 12, 20)
SET search_path = lab07_modeling;  -- DB mặc định trỏ vào lab03_indexing
SET statement_timeout = '60s'; SET lock_timeout = '5s';
DROP TABLE IF EXISTS erd_payment_transactions, erd_orders;
-- Entity "đơn hàng": có id, trạng thái (vòng đời) và cột kỹ thuật.
CREATE TABLE erd_orders (
  id          bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  code        text NOT NULL UNIQUE,
  status      text NOT NULL DEFAULT 'NEW' CHECK (status IN ('NEW', 'PAID', 'CANCELLED')),
  total       numeric(14,2) NOT NULL CHECK (total >= 0),
  version     int NOT NULL DEFAULT 0,
  created_at  timestamptz NOT NULL DEFAULT now(),
  updated_at  timestamptz NOT NULL DEFAULT now()
);
-- Entity "giao dịch thanh toán": sinh ra SAU đơn hàng nên giữ cột tham chiếu order_id (slide 12).
-- order_id được phép NULL vì giao dịch ủng hộ (donate) không có đơn hàng.
CREATE TABLE erd_payment_transactions (
  id          bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  kind        text NOT NULL CHECK (kind IN ('ORDER', 'DONATE')),
  order_id    bigint REFERENCES erd_orders (id),
  amount      numeric(14,2) NOT NULL CHECK (amount > 0),
  status      text NOT NULL DEFAULT 'PENDING' CHECK (status IN ('PENDING', 'SUCCESS', 'FAILED')),
  version     int NOT NULL DEFAULT 0,
  created_at  timestamptz NOT NULL DEFAULT now(),
  updated_at  timestamptz NOT NULL DEFAULT now(),
  CHECK ((kind = 'ORDER') = (order_id IS NOT NULL))   -- thanh toán đơn thì phải có order_id, donate thì không
);
CREATE INDEX ON erd_payment_transactions (order_id);  -- PG không tự tạo index cho cột FK (chặng 3)
-- #endregion

Bây giờ đọc ngược lại: ERD không chỉ nằm trên giấy, PG lưu nó trong catalog. Region catalog liệt kê cột của 2 bảng và mọi khóa ngoại giữa chúng.

-- #region catalog · Đọc ERD ngược từ catalog: bảng, cột, khóa ngoại (slide 7)
SET search_path = lab07_modeling;  -- DB mặc định trỏ vào lab03_indexing
SET statement_timeout = '60s'; SET lock_timeout = '5s';
SELECT c.relname AS bang, a.attname AS cot, format_type(a.atttypid, a.atttypmod) AS kieu, NOT a.attnotnull AS cho_phep_null
FROM pg_class c JOIN pg_attribute a ON a.attrelid = c.oid AND a.attnum > 0 AND NOT a.attisdropped
WHERE c.relnamespace = 'lab07_modeling'::regnamespace AND c.relname IN ('erd_orders', 'erd_payment_transactions')
ORDER BY c.relname DESC, a.attnum;
SELECT conrelid::regclass AS bang_con, confrelid::regclass AS bang_cha, pg_get_constraintdef(oid) AS dinh_nghia
FROM pg_constraint
WHERE contype = 'f' AND connamespace = 'lab07_modeling'::regnamespace AND conrelid::regclass::text LIKE 'erd_%';
-- #endregion

Chuẩn hóa 0NF → 3NF trên phiếu đơn northwind, rồi phi chuẩn hóa có kiểm soát

Mục tiêu: tự tay gây ra 3 loại bất thường (sửa, xóa, thêm) trên một bảng phẳng, tách nó tới 3NF, chứng minh tách không mất dữ liệu, rồi cố ý thêm một cột dư và bắt được lúc nó lệch.

LÀ GÌ?
Chuẩn hóa: mỗi sự thật chỉ nằm ở một chỗ. 1NF: mỗi ô một giá trị. 2NF: cột không phải khóa phụ thuộc vào toàn bộ khóa. 3NF: không phụ thuộc bắc cầu qua một cột không phải khóa.
TẠI SAO?
Một sự thật chép N lần thì phải sửa N lần; quên một lần là dữ liệu tự mâu thuẫn, và không ai biết bản nào đúng.
KHI NÀO KHÔNG?
Màn hình đọc rất nhiều và phép tính đắt (danh sách đơn kèm tổng tiền, báo cáo): thêm cột cache, nhưng phải có chỗ cập nhật duy nhất và câu đối soát.

Mục tiêu: đo cái giá thật của FK, thấy PG không tự index cột FK, rồi chạy race 2 phiên để thấy đề xuất "bỏ FK, kiểm tra ở app" của slide 11 để lại dữ liệu mồ côi.

LÀ GÌ?
FK là ràng buộc DB tự kiểm tra: ghi bảng con thì cha phải tồn tại; xóa hoặc đổi khóa bảng cha thì không được còn con. Reference column chỉ là cột chứa id, không ai kiểm tra.
TẠI SAO?
Kiểm tra ở app là "đọc rồi ghi" bằng hai câu riêng; giữa hai câu, phiên khác chen vào. FK kiểm tra ngay trong DB và khóa dòng cha trong lúc kiểm tra.
KHI NÀO KHÔNG?
Hai bảng nằm ở hai DB/service khác nhau (FK không vượt được ranh giới DB), hoặc bảng log ghi cực nhiều mà mồ côi vô hại. Khi đó dùng reference column + job đối soát.
Slide 11 · Cần sửa
Slide nói

FK bắt DB kiểm tra khóa được tham chiếu mỗi lần insert/update, làm schema phức tạp, app phải bắt exception để biết lý do, backup phức tạp. Giải pháp ("ý kiến của tôi"): bỏ FK, tự kiểm tra ở tầng app. Ghi chú: Foreign Key ≠ Reference Column.

Làm mẫu · đọc filenode để biết PG có viết lại bảng không
  1. Filenode là tên file vật lý của bảng trên đĩa. PG viết lại bảng = tạo file mới = filenode đổi. Bảng ddl_events ghi filenode sau mỗi bước.

  5. Đổi int → bigint làm mỗi dòng dài thêm 4 byte, cũng phải viết lại: 34036, 518.812 ms.

Quy tắc rút ra: thêm cột cho phép NULL hoặc có default không đổi theo dòng thì rẻ. Default "volatile" (random(), gen_random_uuid()) và đổi kiểu thì đắt, tỉ lệ thuận với số dòng.

PG 16 đo được

Làm mẫu · vì sao tiền không bao giờ là float
  1. Chạy region money bên dưới. Dòng đầu: 0.1 + 0.2 bằng float ra 0.30000000000000004, và phép so sánh với 0.3 ra f. Lý do: 0,1 không biểu diễn đúng được trong hệ nhị phân, máy lưu số gần nhất.
  2. Sai số nhỏ cộng dồn: cộng 0,1 một triệu lần ra 100000.00000133288, còn numeric ra đúng 100000.0.
  3. Dữ liệu thật: northwind lưu đơn giá và chiết khấu bằng real. So cùng một cách tính mới công bằng. Không làm tròn: float ra 1265793.038653364, numeric ra 1265793.0395, lệch chưa tới 0,001. Làm tròn từng dòng về 2 số lẻ như in hóa đơn: float ra 1265792.95, numeric ra 1265793.29. Float cho ra những giá trị kiểu 0,0749999 nên làm tròn sai ở các dòng "x,xx5", cộng lại lệch hẳn 34 xu so với sổ sách.
  4. Kết luận cho quán: giá món là numeric(12,2) (hoặc bigint đếm đồng, vì VND không có xu). Prisma: Decimal @db.Decimal(12,2), ở Node đọc ra là Decimal, đừng ép sang number trước khi cộng.

WITH RECURSIVE
  i(n, lo, hi) AS (SELECT 0, 1000::bigint, 2000::bigint UNION ALL SELECT n + 1, lo, (lo + hi) / 2 FROM i WHERE (lo + hi) / 2 NOT IN (lo, hi)),
  d(n, lo, hi) AS (SELECT 0, 1000::float8, 2000::float8 UNION ALL SELECT n + 1, lo, (lo + hi) / 2 FROM d WHERE (lo + hi) / 2 NOT IN (lo, hi)),
  f(n, lo, hi) AS (SELECT 0, 1000::float4, 2000::float4 UNION ALL SELECT n + 1, lo, ((lo + hi) / 2)::float4 FROM f WHERE ((lo + hi) / 2)::float4 NOT IN (lo, hi))

View: PG trải phẳng view, hay phải tính riêng?

Mục tiêu: đọc EXPLAIN để biết một view được PG "trải phẳng" vào câu lệnh (giống MERGE của MySQL) hay bị tính riêng rồi mới lọc (giống TEMPTABLE). Chặng này tùy chọn: thiếu giờ thì để tối, chặng 8 không cần nó.

LÀ GÌ?
View là một câu SELECT có tên, không lưu dữ liệu. Mỗi lần bạn đọc view, PG chép câu SELECT đó vào câu lệnh của bạn.
TẠI SAO?
Gói JOIN dài thành một tên ngắn, cấp quyền theo cột, giữ tên cũ khi đổi bảng. Với view đơn giản thì gần như không tốn gì: plan giống hệt khi viết JOIN tay.
KHI NÀO KHÔNG?
Khi view có LIMIT, window function hay DISTINCT ON mà bạn lại lọc từ bên ngoài: PG phải tính cả view trước. Lúc đó viết thẳng câu truy vấn, hoặc đưa điều kiện vào trong view.

Quan hệ đa hình: một bình luận thuộc về bài viết hoặc món






Nếu bạn bỏ qua chặng 7 (view) thì không sao: chặng này chỉ dùng FK, CHECK và index từ chặng 3–5.


Mục tiêu: so ba cách lưu "bình luận thuộc về bài viết hoặc sản phẩm", đếm bình luận mồ côi của từng cách sau khi xóa bài viết #1, và chọn được cách để dùng với Prisma.




LÀ GÌ?
Quan hệ đa hình (polymorphic): một dòng con có thể trỏ tới một trong nhiều bảng cha. Ví dụ ở chuỗi F&B: bình luận cho bài khuyến mãi hoặc cho một món.


TẠI SAO?
Cách hay gặp nhất (cột commentable_type + commentable_id, kiểu Rails/Laravel) không thể khai báo FK. DB không còn giữ được toàn vẹn, và lỗi chỉ lộ ra khi đếm mồ côi.


KHI NÀO KHÔNG?
Khi chỉ có một loại cha thì dùng một FK thường. Khi số loại cha lớn và đổi liên tục (log, audit) thì type + id chấp nhận được, miễn là bạn có job đếm mồ côi.

Capstone: sổ cái kép cho ví khách hàng






Mục tiêu: dựng wallets, transfers, ledger_entries để DB tự chặn 4 kiểu tấn công, đối soát được số dư cache, và giao dịch ngược chiều không deadlock.




LÀ GÌ?
Sổ cái kép (double-entry): mỗi lần chuyển tiền ghi 2 bút toán, âm ở ví nguồn, dương ở ví đích, tổng bằng 0. Số dư = tổng bút toán của ví.


TẠI SAO?
Chỉ sửa cột balance thì sai một lần là mất dấu. Có sổ cái thì mọi đồng tiền có nguồn gốc và số dư sai tính lại được.


KHI NÀO KHÔNG?
Bộ đếm lượt xem, điểm không quy ra tiền: một cột n = n + 1 là đủ.

-- Kiểm tra "tổng các bút toán của một giao dịch = 0" lúc COMMIT (DEFERRED): code có thể ghi hai bút toán bằng hai câu lệnh riêng,
-- sau câu đầu tổng tạm thời khác 0. (post_transfer ghi cả hai trong MỘT câu INSERT nên kiểm tức thì cũng qua.)
CREATE OR REPLACE FUNCTION ledger_check_balanced() RETURNS trigger LANGUAGE plpgsql AS $$
BEGIN
  IF (SELECT sum(amount) FROM lab07_modeling.ledger_entries WHERE transfer_id = NEW.transfer_id) <> 0 THEN
    RAISE EXCEPTION 'giao dịch % lệch: tổng bút toán khác 0', NEW.transfer_id USING ERRCODE = '23514';
  END IF;
  RETURN NULL;
END $$;
CREATE CONSTRAINT TRIGGER ledger_balanced AFTER INSERT ON ledger_entries
  DEFERRABLE INITIALLY DEFERRED FOR EACH ROW EXECUTE FUNCTION ledger_check_balanced();
-- Sổ cái chỉ được THÊM: sửa sai bằng bút toán đảo (refund), không UPDATE/DELETE bút toán cũ.
CREATE OR REPLACE FUNCTION ledger_append_only() RETURNS trigger LANGUAGE plpgsql AS $$
BEGIN
  RAISE EXCEPTION 'ledger_entries chỉ được thêm, không được %', TG_OP USING ERRCODE = '23001';
END $$;
CREATE TRIGGER ledger_no_update_delete BEFORE UPDATE OR DELETE ON ledger_entries
  FOR EACH ROW EXECUTE FUNCTION ledger_append_only();
-- Ghi một giao dịch chuyển tiền: khóa 2 ví theo thứ tự id (Bài 14), ghi 2 bút toán, cập nhật số dư cache.
CREATE OR REPLACE FUNCTION post_transfer(p_from bigint, p_to bigint, p_amount numeric, p_key text, p_order_ref text DEFAULT NULL)
RETURNS bigint LANGUAGE plpgsql AS $$
DECLARE v_id bigint;
BEGIN
  PERFORM 1 FROM lab07_modeling.wallets WHERE id IN (p_from, p_to) ORDER BY id FOR UPDATE;
  INSERT INTO lab07_modeling.transfers (idempotency_key, order_ref, amount) VALUES (p_key, p_order_ref, p_amount) RETURNING id INTO v_id;
  INSERT INTO lab07_modeling.ledger_entries (transfer_id, wallet_id, amount) VALUES (v_id, p_from, -p_amount), (v_id, p_to, p_amount);
  UPDATE lab07_modeling.wallets SET balance = balance - p_amount, version = version + 1, updated_at = now() WHERE id = p_from;  -- trừ trước
  UPDATE lab07_modeling.wallets SET balance = balance + p_amount, version = version + 1, updated_at = now() WHERE id = p_to;    -- cộng sau
  RETURN v_id;
END $$;
-- #endregion

CREATE OR REPLACE FUNCTION refund(p_transfer_id bigint) RETURNS bigint LANGUAGE plpgsql AS $$
DECLARE v_from bigint; v_to bigint; v_amount numeric; v_ref text;
BEGIN
  SELECT max(e.wallet_id) FILTER (WHERE e.amount < 0), max(e.wallet_id) FILTER (WHERE e.amount > 0),
         max(e.amount), max(t.order_ref)
    INTO v_from, v_to, v_amount, v_ref
  FROM lab07_modeling.ledger_entries e JOIN lab07_modeling.transfers t ON t.id = e.transfer_id
  WHERE e.transfer_id = p_transfer_id;
  IF v_amount IS NULL THEN
    RAISE EXCEPTION 'không có giao dịch %', p_transfer_id USING ERRCODE = 'P0002';
  END IF;
  -- đảo chiều; khóa theo id và UNIQUE idempotency_key do post_transfer lo
  RETURN lab07_modeling.post_transfer(v_to, v_from, v_amount, 'refund-' || p_transfer_id, v_ref);
END $$;
