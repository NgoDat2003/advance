Vì sao Redis nhanh, và vì sao một lệnh chậm làm đứng cả server

Mục tiêu: tự thấy Redis chạy mọi lệnh trên một luồng (I/O threads đang tắt), thấy một lệnh 2 giây bắt client khác đứng chờ, rồi đo thứ gì thật sự làm chậm: số vòng mạng, kích thước value, hay số lệnh.

LÀ GÌ?
Redis là kho dữ liệu trong RAM. Một vòng lặp epoll theo dõi mọi socket, còn một luồng chính chạy lần lượt từng lệnh của mọi client.
TẠI SAO?
Một luồng nên mỗi lệnh đã nguyên tử, không cần khóa bên trong. Cái giá: một lệnh chậm (KEYS *, xóa big key, Lua chạy lâu) chặn tất cả, kể cả kết nối mới.
KHI NÀO KHÔNG?
Đừng nghĩ "Redis nhanh nên gọi bao nhiêu cũng được": mười lệnh gửi lần lượt tốn mười vòng mạng, gộp lại (pipeline, MGET) mới nhanh. Không bao giờ quét cả keyspace trên production.
Tình huống · tối thứ sáu ở chuỗi F&B

7 giờ tối, 40 máy POS đang gọi Redis lấy giỏ hàng và giá món. Một bạn admin gõ KEYS * trên production "để xem có bao nhiêu khóa". Mọi máy POS đứng hình vài giây, log không có lỗi, CPU của app vẫn thấp. Lý do: Redis chỉ có một luồng chạy lệnh, và luồng đó đang bận với KEYS. Chặng này dựng lại cảnh đó, an toàn hơn, bằng DEBUG SLEEP.

Tùy chọn (10 phút) · xem trước Lua — học kỹ ở chặng 8: script 6 giây, BUSY và SCRIPT KILL

Lua cũng chạy trên luồng chính. Script dưới lặp tới khi đồng hồ Redis qua 6 giây. Quá busy-reply-threshold (mặc định 5 giây, đồng hồ server), mọi lệnh khác nhận BUSY, trừ SCRIPT KILL và SHUTDOWN NOSAVE. B chạy trong Git Bash (01-block.B.sh), mỗi dòng mở một kết nối mới, và kết nối mới cũng nhận BUSY. Thứ tự: busy-reset ở A, busy của B (dòng đầu chờ barrier), rồi busy ở A.

UNLINK l06:barrier:block-busy
# #region busy · B gặp BUSY rồi dừng script của A bằng SCRIPT KILL (slide 13)
docker exec advance-be-redis redis-cli BLPOP l06:barrier:block-busy 5
set -u
sleep 0.5
# --no-raw để redis-cli in "(error) …" giống terminal tương tác. Câu trả lời tới sau khoảng 5 s (busy-reply-threshold).
docker exec advance-be-redis redis-cli --no-raw PING
docker exec advance-be-redis redis-cli --no-raw SCRIPT KILL
# #endregion
RPUSH l06:barrier:block-busy go
EVAL "local function now() local t = redis.call('TIME') return t[1] * 1000000 + t[2] end local s = now() while now() - s < 6000000 do end return 'xong'" 0

Đồng hồ host: A gửi EVAL lúc +398, BUSY về B lúc +5017; redis-cli trong container đo EVAL (5.79s). Hai đồng hồ lệch vì đồng hồ máy ảo Docker chạy nhanh hơn Windows (chặng 8 dùng chuyện này khi nói về Redlock), nên chỉ nói: BUSY bắt đầu khoảng 5 giây sau khi script chạy, phụ thuộc máy. SCRIPT KILL dừng được vì script chưa ghi gì; đã ghi thì chỉ còn SHUTDOWN NOSAVE.

Tự làm · chặng 1

Đề: dựng lại sự cố KEYS *. Tạo 200000 khóa giả trong vùng riêng l06:my:*, rồi so KEYS với SCAN trong khi terminal B đo độ trễ liên tục (mỗi giây một dòng min, max, avg). Dọn khóa giả khi xong.

# Terminal A (Git Bash)
docker exec advance-be-redis redis-cli DEBUG POPULATE 200000 l06:my:pop
docker exec advance-be-redis redis-cli DBSIZE
docker exec advance-be-redis redis-cli SLOWLOG RESET

# Terminal B (PowerShell; Git Bash thêm winpty phía trước), để chạy, Ctrl+C để dừng
docker exec -it advance-be-redis redis-cli --latency-history -i 1

# Terminal A, trong lúc B đang in
time docker exec advance-be-redis redis-cli KEYS 'l06:my:*' | wc -l
sleep 3
time docker exec advance-be-redis redis-cli --scan --pattern 'l06:my:*' | wc -l
docker exec advance-be-redis redis-cli --no-raw SLOWLOG GET 5

# Dọn khóa giả (chỉ đụng l06:my:pop:*)
docker exec advance-be-redis sh -c "redis-cli --scan --pattern 'l06:my:pop:*' | xargs -r -n 1000 redis-cli UNLINK" | tail -1

PASS khi: (1) SLOWLOG GET 5 có mục KEYS l06:my:* (thời gian ở dòng 3)) và không có mục SCAN; (2) ở cửa sổ chứa KEYS, max của B xấp xỉ thời gian KEYS đổi ra ms, còn lúc --scan thì max vẫn nhỏ như bình thường; (3) hai lệnh đếm cùng số dòng (ít nhất 200000).

Đáp án và giải thích

KEYS là một lệnh duyệt hết keyspace rồi mới trả lời, nên suốt lúc đó luồng chính không làm gì khác và max của B nhảy lên đúng khoảng đó. --scan gọi SCAN nhiều lần, mỗi lần một ít khóa, nên PING của B chen vào được giữa hai lần gọi. Tổng thời gian có thể dài hơn, nhưng không lần nào chặn lâu hay đủ chậm để vào SLOWLOG.

Nếu KEYS dưới 10 ms trên máy bạn, tạo thêm DEBUG POPULATE 200000 l06:my:pop2 rồi chạy lại (nhớ dọn cả l06:my:pop2:*). Ở production: cấm KEYS bằng ACL, duyệt khóa bằng SCAN.
