C. Bên trong trang B+tree (pageinspect): gốc = khóa phân cách + trang con, lá = khóa + TID heap

   => ✔ Mục ở gốc chỉ có khóa + số trang con, không có TID heap: dữ liệu chỉ nằm ở lá (B+tree, slide 10)
   => ✔ TID trong lá = ctid thật của dòng = (11082,43): index PostgreSQL trỏ thẳng tới địa chỉ vật lý (block, offset)
   => ✔ 3 trang index (gốc → lá) + 1 trang heap = 4, khớp 4 trang EXPLAIN đếm ở phần A
   => ✔ Các lá nối nhau theo thứ tự khóa: quét dải chỉ việc đi sang phải, không quay lại gốc (vì vậy phần B rẻ)

D. Hash index trên users(email), trong BEGIN … ROLLBACK: chỉ phục vụ phép "="
─────────────────────────────────────────────────────────────────────────────
│ Truy vấn                                  │ Kế hoạch                          │    Dòng │  Trang │    ms │
├───────────────────────────────────────────┼───────────────────────────────────┼─────────┼────────┼───────┤

Kích thước / thời gian dựng: hash 32.0 MB / 1.8 s · btree 38.8 MB / 1.3 s
   => ✔ Phép "=": planner chọn hash, 2 trang (bucket + heap) so với btree 4 trang (đi qua mọi tầng rồi tới heap)
   => ✔ Range và ORDER BY vẫn Seq Scan dù đã ép tắt Seq Scan: hash chỉ lưu mã băm, không giữ thứ tự khóa (slide 12)
   => ✔ Hash 32.0 MB so với btree 38.8 MB: hash lưu mã băm 4 byte thay vì cả chuỗi email
